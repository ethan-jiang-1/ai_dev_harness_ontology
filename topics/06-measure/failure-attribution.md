# 尺子二：失败出在哪一环

## 问题

一个任务失败了，最常见的归因是「模型不够强」。这个归因不可证伪，也不可操作——它给不出下一步动作。

另一篇工作提出相反的做法：**先诊断工作流。** 它研究 NL → 本体接地 ABox DSL 的语义解析，指出语法有效容易、语义充分很难，而反复出现的难点是结构性的：

| 结构性失败源 | 表现 |
|---|---|
| 输入不足 | 用户描述本身缺关键信息 |
| 领域接地弱 | 词汇没有落到本体的概念上 |
| 模板与词汇缺口 | 输出格式与本体词表不匹配 |
| 校验弱 | 只能发现表面问题 |
| 非局部修复 | 为改一处而扩散到远处，引入新错 |

## 方法上的关键选择

不做笼统的准确率，而是**按角色分别做难度画像**：同一任务里「读输入」「转换」「校验」「修复」是不同角色，失败原因不同。

这条方法论价值高于它的具体结果：**它把「模型不行」拆成了五个可以被工程解决的位置。**

## 「非局部修复」值得单独记

校验弱 → 只能发现表面问题 → 修改扩散 → 引入新错误。这是一条**可归因的因果链**，且根因在 harness（校验太弱），不在模型。

它解释了一个常见现象：换更强的判定器往往比换更强的模型更有效。因为模型本来能改对，是判定给了它错误的方向。
