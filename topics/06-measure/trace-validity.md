# 尺子三：过程是不是真的有效

## 问题

形式化器的设计初衷是：模型负责把问题写成程序，求解器负责搜索并给出保证。**判据通常是「程序输出对不对」——但这看不出程序是在搜索，还是在复述。**

SLB 研究揭示第二种情况很普遍：在写程序之前，推理轨迹里已经在赋值、试算、排除变量取值，常常一路算到最终答案；程序只是把答案重述一遍。

## 两种伤害

1. **成本随实例增长。** 约束满足是 NP 完全的；在 token 里求解，token 消耗随实例规模增长（Meeting Planning 上接近三倍）。
2. **保证失效。** 求解器本该提供模型推理所缺的保证；若程序只复述轨迹答案，这层保证就不存在了。

## 尺子的问题在哪

只看输出正确与否的判据，**结构上无法区分**这两种程序。这就是「尺子选错」的典型：不是测不准，是测不到。

本仓库的推论：**任何只看最终产物的判据，都会放过冗余与错误继承。** 要看见它们，判据必须能读中间（轨迹、程序、检索路径）。

## 一个待核的干预

综述转述：隐藏输入数值可消除极大部分 SLB。若成立，说明 SLB 很大程度上是「模型看见了具体数值就忍不住去算」——这是一个可操作的设计线索（给结构不给数值）。

数字（85% 轨迹 / 24% token / 9% 错误继承 / 97% 消除）均来自转述，**待核**。

## 与其它派的关系

- 为 [02 判定](../02-judgment/README.md) 提供设计约束：判定器要能接受轨迹作为输入，而不只是最终输出。
- 为 [04 状态](../04-state/README.md) 的「错误继承」提供机制解释：一旦上游答案被当作既定事实，下游程序会把它一起继承。
