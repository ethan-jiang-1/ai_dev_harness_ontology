# 投影：把本体写成它读得懂的东西

## 问题

本体是给机器推理用的结构，模型吃的是文本。中间这一步——**怎么把结构翻译成文本**——决定了本体能不能被真正使用，而它通常被当成实现细节跳过。

## 机制：同一份知识的四种交付形态

Narrow & Deep 在同一台真实低湿空气处理试验台上，把同一座本体塔（162 节点 / 217 边）用四种形态交给 agent：

| 形态 | 体积 | element score（pooled） | 关键条件 |
|---|---|---|---|
| **投影文本**（放 prompt） | 约 45k 字符 | **0.777** | 四个模型都有效 |
| 整塔 JSON | 约 99k 字符 | 0.717 | 结构化但长 |
| 塔查询工具 | 按需 | 0.638 | 只在模型调用时有用（76/108 trials） |
| 文档检索 | 1.5M 字符语料 | 0.597 | 检索工具在 21/108 trials 才被调用 |

**关键数字**：

- K0（地址级）→ K1（tag 名 + 单位）：避坑率 **+54.6 pp**。**命名和单位本身就是最大的一层知识。**
- K1 → K2（投影文本）：避坑率 **0.605 → 0.802（+19.8 pp，95% CI +3.0~+38.4）**，element score **0.566 → 0.777**，OR 5.45，Holm p=6.0×10⁻⁷。
- 四个模型（9B–750B）的 element gain：+0.235 / +0.178 / +0.213 / +0.219；**H2（增益随容量上升）未被支持（p=0.85）**。
- **9B 带投影 0.737 > 最大模型不带投影 0.672**；但任务限定「答案基本写在文本里」。
- 打乱句序：0.685；JSON 0.717；文档检索 0.597；查询工具 0.638。

**结论**：投影不是「换格式」，是**把绑定、归纳、排序工作提前做掉**。文本投影在四个模型上都有效；查询工具只服务会调用它的模型；文档检索最弱。

## 一个反直觉的细节

操作经验有三种处理方式：写进本体（成为知识节点）、作为记录放进提示、留在原始日志里。

- 写进本体 → 被使用。
- 作为记录放进提示 → 也基本被使用。
- 留在原始日志里 → **4/80 次诊断 trial 才被检索**；两个模型从未调用。

差别不在内容，在**是否已被提升为「结论形态」**，以及**由谁决定检索**：并入本体是抽取时（系统控制）；留在日志是查询时（agent 控制）。原始日志需要模型自己完成「从事件到教训」的归纳，而这一步它常常不做。

推论：**投影不只是换格式，是把归纳工作提前做掉。**

## 成本与决策规则

| 成本 | 说明 |
|---|---|
| 塔构建 | 每系统一次性；42 tags / 34 assumptions / 24 knowledge / 16 derivations；人工 curator |
| 投影生成 | 约 45k 字符；从描述记录生成；本文未量化自动化程度 |
| 日志并入 | 持续；新教训写成 knowledge node，否则退回检索 |
| 维护 | 本体/投影/知识节点要同步；否则模型学到旧规则 |

**什么时候投影划算**：

- 知识窄而深、答案基本写在知识里（规则/手册/设备参数/运行教训）。
- 模型要在现场跑（open-weight 9B 也有效）。
- 你能承担人工建模与维护。
- 你不需要每条陈述都可追溯到节点；需要时用查询工具，但要接受「只有会调用的模型受益」。

**什么时候别投影**：答案要从大语料检索发现；知识是开放域、长尾；投影体积会撑爆预算；本体/投影没人维护；需要强约束（投影仍是弱端，能被忽略）。

## 失效模式

- **投影即答案，则基准偏慷慨。** 若任务答案基本就写在投影文本里，测出的是「抄得准不准」，不是「理解得对不对」。作者自己指出了这一点。
- **投影体积失控。** 本体越大，投影越长，最后吃光预算——此时它退化成本派的弱端。N&D 的 45k 字符已经接近一个中型上下文；多系统/多年日志会更大。
- **投影丢掉约束关系。** 只有概念和属性、没有「A 成立则 B 不成立」的投影，等于给了知识没给规则。
- **投影与本体不同步。** 本体改了、投影没重生成，模型学到的是旧规则。
- **投影不可追溯。** 文本里的陈述不能指回来源；查询工具能，但不是所有模型会用。N&D 的 9B/EXAONE 在查询工具下反而更差。
- **把投影当约束。** 投影仍在上下文里，能被忽略；安全层必须独立于 agent（N&D 的 live runs 就是证据：25/61 命令被安全层拒绝，24–68% 事实主张无证据支持）。

## 与其它派的关系

- 投影是 [03 知识派](../README.md) 的默认形态。
- 投影的产物一旦进入上下文，就落回**弱约束**——它能被忽略。要它硬起来，得进 [01 约束](../../01-constraint/README.md) 或 [02 判定](../../02-judgment/README.md)。
- 「把归纳提前做掉」这件事，与 [05 生产](../../05-produce/README.md) 的精化是同一动作的两种时机。
- 与 [编译](../compilation/README.md) 的分界：投影投的是**领域知识**（规则/手册/设备）；编译投的是**证据**（claim + span）。CAI 的「compile evidence, not prose」是这条分界的操作版。

## 开放问题

- 投影长度与遵守率的关系是线性的还是有拐点？45k 字符之后呢？
- 结构化记录（YAML/表格）与自然语言段落，哪种更不容易被忽略？N&D 的 JSON 0.717 < 文本 0.777，提示「顺序/叙述」本身有信息。
- 能否自动生成「投影」并保证与本体同步？这是 [05 生产](../../05-produce/README.md) 的一个子问题。
- 投影 + 查询工具能否兼得「可用性 + 可追溯性」？例如文本每句带节点 id。
- 多设备 common tower + instance tower 的投影怎么组织？会不会反而失去「窄而深」。
