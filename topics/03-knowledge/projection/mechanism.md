# 投影 · 机制

> 只写「它怎么跑」。判断回 [findings](./findings.md)，边界/下一步回 [frontier](./frontier.md)。

## 问题

本体是结构，模型吃文本。中间这一步决定本体能不能被使用，通常被当实现细节跳过。

## 同一份知识的四种交付形态（N&D）

| 形态 | 体积 | element score（pooled） | 关键条件 |
|---|---|---|---|
| 投影文本（prompt） | 约 45k 字符 | **0.777** | K1→K2 四模型均为正 |
| 整塔 JSON | 约 99k 字符 | 0.717 | 结构化但长 |
| 塔查询工具 | 按需 | 0.638 | 只在模型调用时有用（76/108 trials） |
| 文档检索 | 整厂日志/文档语料 | 0.597 | 检索工具在 21/108 trials 才被调用 |

> K2-json 与 K2-tool 是事后描述性比较（K2-tool 明确不在 1,304 预注册批次内），且 JSON 约 99k、含 16 个推导量/假设，长度与内容都不同；pooled 排序不是普适规律：GLM-5.2 的 JSON 0.900 > 文本 0.891，Qwen 的工具 0.407 < 文档 0.538。文本在四个模型上都拿到正增益（K1→K2：+0.235 / +0.178 / +0.213 / +0.219），但这不等于「所有模型上文本 > JSON/工具」。

## 关键数字

- K0（地址级）→ K1（tag 名 + 单位）：避坑率 **+54.6 pp**。**命名+单位是已测得的最大一层知识**；塔的物理深度（16 个推导量/假设）不在投影里、9 个任务也不要求推导量，未测，不能与它排序（§5.1–5.2）。
- K1 → K2（投影文本）：避坑率 **0.605 → 0.802（+19.8 pp，95% CI +3.0~+38.4）**，element score **0.566 → 0.777**，OR 5.45，Holm p=6.0×10⁻⁷。
- 四个模型（9B–750B）的 element gain：+0.235 / +0.178 / +0.213 / +0.219；H2（随容量上升）未支持（p=0.85）。
- **9B 带投影 0.737 > 最大模型不带投影 0.672**（区间约 0.3 宽，不能当普遍规律）；且任务限定「答案基本写在文本里」。
- 打乱句序 0.685；JSON 0.717；文档检索 0.597；查询工具 0.638（pooled；JSON/工具为事后比较，排序有模型级反转）。

## 操作经验的两种处理

- 抽取时并入本体 → 被使用：移除已并入的教训，element score −0.20（SE 0.05）。
- 留在原始日志 → **4/80 次诊断 trial 才被检索**；两个模型从未调用。
- **H3（预注册）：本事故记录提高诊断分 → 未支持。** K4 0.644 vs K4x 0.645（element score，4 个诊断任务，差 <0.01）；K4x 是 H3 的操纵条件，不是探索性比较（§5.6）。K4 是累积条件，两臂只有「日志里有没有本事故记录」一处差别、投影相同，所以这组只隔离「日志里的本事故记录」，不能回答「检索整个日志有没有用」。零结果与 4/80 的检索率一致：**「可检索」不等于「会被用到」**。

本页只按 digest 的两条路径写；「把记录放进提示」不在 digest 条目内，不补这一臂。

差别在**由谁决定检索**：并入本体是抽取时（系统控制），留在日志是查询时（agent 控制）。论文测到的是「谁决定检索」（系统 vs agent），不是「agent 不做归纳」的因果（N&D §4.4）。

推论（`推测`）：**投影不只是换格式，是把归纳工作提前做掉。**

| 成本 | 说明 |
|---|---|

| 投影生成 | 约 45k 字符；从描述记录生成；自动化程度未量化 |

## 失效模式

- **投影即答案，则基准偏慷慨。** 任务答案基本写在投影里，测的是「抄得准不准」，不是「理解得对不对」。
- **投影体积失控。** 45k 字符已接近中型上下文；多系统/多年日志会更大。
- **投影丢掉约束关系。** 只有概念/属性、没有「A 成立则 B 不成立」，等于给知识没给规则。
- **投影与本体不同步。** 本体改了、投影没重生成，模型学到旧规则。
- **投影不可追溯。** 文本陈述不能指回来源；查询工具能，但不是所有模型会用（Qwen 的工具分 0.407 低于其文档检索 0.538；EXAONE 只调了 2/27 次）。
- **把投影当约束。** 投影在上下文里，不承担拒绝逻辑；安全层必须独立（25/61 条到达命令被拒；24–68% 事实主张无证据**仅 GLM-5.2**，gpt-5.6-sol 4–19%）。「投影写了规则仍会被忽略」未做 prompt-vs-code 对照（`推测`）。

## 与本体 / 回路的关系

本体在投影里以 **领域知识文本** 出现；不承担硬约束，覆盖率取决于投影是否包含规则/约束。live run 故意不告知 agent 限值，25/61 条命令被安全层拒绝；「投影能被忽略」本身未做对照（`推测`），被违反时通常没有自动信号。

## 实施与客户价值（A3/A4）

> 本节引用的分数、字符数、拒绝率均出自 N&D digest（`已核`，条件见该文 §4–§5）；凡标 `推测` 的是本页的成本/价值估算、建议阈值或工程配方，不是论文数字。如果只留一句：**先用两周验证「命名+单位」够不够，再决定要不要建塔和投影。**

### 实施决策

1. **预算顺序：先做命名+单位（K1），再决定建不建塔与投影。** K0→K1 是 +54.6 pp，K1→K2 只有 +19.8 pp（N&D §4.1）。如果本厂 3 个代表性任务的 primary trap 在 K1 就基本消失，建塔的边际收益覆盖不了 curator 成本，应停在 K1。这条改变的是「本体项目从哪一步立项」，不是「投影怎么写」。
2. **默认交付形态选固定分节的文本投影（工程建议，不是论文结论）；整塔 JSON / 查询工具 / 文档检索只在有明确理由（可追溯、模型反转）时选。** 「更便宜」常被当成选它们的理由，但 N&D 没有做成本对照，token 成本未测（`推测`）。同一塔上 0.777 / 0.717 / 0.638 / 0.597（Table 2）。但这几项是事后描述性比较，且 GLM-5.2 的 JSON 0.900 高于其文本 0.891——所以决策应是「默认文本 + 允许按模型/任务复测 JSON」，不是全局禁用 JSON。
3. **把投影顺序当接口冻结，不当排版细节。** 打乱句序 0.777→0.685，说明顺序本身是有效成分；生成器必须固定分节顺序并版本化，评审时把顺序变更按行为变更处理。
4. **运行教训在抽取时并入，不把「让 agent 自己查日志」当知识供给方案。** 日志检索 4/80 次被调用，两个模型从未调用；移除已并入教训 element −0.20（SE 0.05）。预注册 H3（本事故记录提高诊断分）未支持：K4 0.644 vs K4x 0.645（差 <0.01）；两臂投影相同，只差日志里有没有本事故记录，所以这组只隔离日志记录。这条改变 knowledge owner 的工作时点：从「查询时由 agent 归纳」改为「入库时由 curator 归纳」。
5. **投影不承担安全边界，硬约束另实现。** 25/61 条到达安全层的命令被拒，至少 4/14 次运行报告了未发生的变更（N&D §4.3）——agent 自述不能作为控制依据。投影里可写允许列表/限值作提示，但拒绝逻辑必须在代码里，不能因为投影写了就认为已约束。

### 数据/接口

**生成器输入**：与塔同源的描述记录（sensor registry、couplings、control-point ontology、system targets），加上六类节点的字段——tag 的 `label/unit/quality_flag`，binding 的 `plc_address/raw_scale/unit/defined_at`，assumption 的 `statement/scope/review_due`，derivation 的 `inputs/formula/unit/assumptions/level`，knowledge 的 `event/lesson/linked_nodes/date`。

**投影头（必填）**：`system_id`、`tower_version`、`projection_version`、`generated_at`、`covered_sections`、`projection_chars`、`rubric_version`。版本号进头是「投影与本体不同步」唯一可检查的点。

**投影体（固定分节顺序）**：① 头部 ② 设备/流程概览 ③ tags/bindings（按 level 排序，同级按名字）④ assumptions（按影响面）⑤ derivations（按 level）⑥ knowledge nodes（日期倒序）⑦ 安全边界（仅提示）。每节自然语言小段，不堆表格；每条陈述末尾带 `[node_id]`。

**可追溯接口**：生成器额外输出 `statement_id → node_id` 映射表（与投影同版本），供抽检与审计；文本自身不能执行的追溯由这张表承担，不靠模型在回答里引用。

**变更触发**：tag 名/单位/binding/assumption/derivation 任一变更 → 重生成并递增 `projection_version`；追加 knowledge node 可增量，但头部版本必须重算。

**写接口（独立安全层，不是投影功能）**：`propose_setpoint(tag, value, reason)` → `{accepted|rejected, checks[], readback}`；载荷含 `tag, value, reason, actor, idempotency_key`；读回写入后的值/时间/操作者。检查顺序：tag 在允许列表 → 值在范围 → 最近无人工写入 → plant guard（绝对限、步长、每小时/累计变化、等待时间）；通过才写，写后读回并记录，拒绝也记录。投影里可写允许列表/限值作提示，但拒绝逻辑必须在代码里。检查顺序与读回 `已核`（论文实际写路径，§3.4）；具体签名与载荷字段是 digest 的工程配方（`推测`，§6.5）。

**可选工具（非默认路径）**：`describe_node(node_id)`、`query_derivation(input_tag, output_quantity)`、`list_knowledge(node_id, since)`。启用前先测调用率与空答率：N&D 里 Qwen 调了 23/27 但 13/27 空答，工具分 0.407 反而低于其文档检索 0.538。调用率 <20% 时不把审计寄托在工具上（见 stop condition）。

**评估接口**：每个任务登记 `ground_truth_elements[]`、`primary_trap`、`rubric_version`；`primary_trap_avoidance` 与 `element_score` 分开报；judge 模型、判的是什么、κ 的抽样 trial 数入档。N&D 两个 judge 在 primary-trap 上 κ=0.819（121 个抽样 trial）；作者与 judge κ=0.696（仅 7 个 trial，低于其预注册 0.7）；element score 的评分者一致性未报。rubric 改版必须换版本号，注册版（0.698→0.842）与修订版（0.605→0.802）不能混报。

### 组织/成本

| 角色（owner） | 负责 | 人日 |
|---|---|---|
| 领域工程师 | tag/单位/绑定审计、primary trap 定义、推导与假设 | 建塔 2–4 人周/162 节点，按 `(节点数/162)^0.7` 伸缩（`推测`，N&D §6.2/§6.5） |
| 后端/平台 | 投影生成器、`statement→node_id` 映射、版本与重生成触发 | 2–3 人日 + 0.5 人日/额外 10k 字符（`推测`） |
| curator / 知识 owner | 把运行教训写成 knowledge node 并挂接 | 0.5–1 人日/月（`推测`） |
| 评测 | 9 任务 rubric、回放、judge 与 κ | 1–2 人周 + GPU（`推测`） |
| 安全层 owner | 允许列表、范围、人工写入、步长/累计/等待检查 | 集成一次性，N&D 未给人日（`推测`：1–2 人周） |

**运行成本**：每轮对话固定多带约 45k 字符投影。token 数与单价 N&D 未给；按中英混合约 3–4 字符/token 粗估，约 1.1–1.5 万 token/轮（`推测`），多设备/多站点按设备数线性叠加。prompt caching 能摊薄重复部分，但命中率未测（`推测`）。成本结构的关键点：投影是「每系统一份」的固定开销，任务量越小，单次摊销越贵——这也是先做 K1 再决定建塔的经济理由。

**建塔成本按节点数伸缩（`推测`）**：`build ≈ 2–4 人周 × (节点数/162)^0.7`。指数 <1 是因为 schema/流程可复用，不是实测曲线（digest §6.5）。162 节点是本例规模（42 tags / 34 assumptions / 33 bindings / 24 knowledge / 16 derivations / 13 plant elements）；不同规模先用本式做量级估算，再用第一个 sprint 的工时记录校准。

**Build / buy / do nothing（`推测`）**：

- **build**：塔 + 投影，TCO = 塔构建 + 投影生成 + 维护 + 安全层集成。
- **buy**：CMMS / 知识图谱平台可买，但**报价与覆盖未测，采购前必须 RFQ**，不能把「可买」当已选方案。
- **do nothing**：只做 K1 命名+单位。
- **决策线**：12 个月收益 > TCO 才建塔；K1 已解决 primary trap 则只做命名+单位；没有工时价/事故成本就先测分母。Brick/SAREF/AAS/ISO 15926 是多实体浅描述，不适合单设备深知识。

### stop condition

开工前就写死，命中即停：

1. **K1 已够用 → 停塔。** 3 个试点任务在 K1 下 primary-trap avoidance 均 ≥ 0.90（本页建议阈值，非论文数字），且剩余 trap 与深知识无关 → 只交付命名/单位修复，不建塔、不做投影。
2. **投影 >60k 字符仍装不下或遵守率下降 → 停。** 转查询工具或按域拆成多份投影；不要靠截断，截断会破坏分节顺序（而顺序是有效成分）。
3. **K2 相对 K1 的提升 <5 pp → 停。** 这是本页 V3 的失败线（沿用 N&D §6.6 的试点失败判据）；不要用 element score 总分掩盖 trap 没动。
4. **维护 >2 人周/月 → 停。** 维护吃掉收益时，退为按季度冻结的静态投影或回到文档检索。
5. **工具调用率 <20% 或空答率高 → 不把审计寄托在工具上。** 日志检索同此：K4 诊断 trial 只 4/80 次调用，K4 vs K4x 的 element score 0.644/0.645（H3 未支持）。改用 `statement→node_id` 映射做审计。
6. **任务核心是物理推导而投影不含推导量 → 不用本方案。** N&D 的投影不含 16 个推导量；这类任务要先把推导写进投影或换表示，效果未测（`推测`）。
7. **经济停止线**：`年省工时 × 工时价 < 塔构建摊销 + 投影生成 + 维护` → 停。今天没有工时价/误判成本就先测分母，不拍板。

### 第一个 sprint

**范围**：2 周、1 台设备、3 个真实任务（2 个读数解释 + 1 个事故诊断）、1 个现场可跑的 9B 级模型 + 1 个 30B+ 对照；只做投影层，不建全塔、不接生产写路径。

| 天 | 做什么 | 产出 |
|---|---|---|
| D1–3 | tag/单位/绑定审计；从历史误判中选 3 个任务的 ground truth 与 primary trap | 审计表 + 任务卡 ×3 |
| D4–6 | 写 3 条 derivation 声明 + 2 条 knowledge node；做约 1/10 规模的塔切片 | 塔切片 + 假设清单 |
| D7–8 | 固定分节生成投影（目标 ≤45k 字符）+ `statement→node_id` 映射；不给 JSON/工具 | 投影 v1 + 映射表 |
| D9–10 | K1 vs K2 回放（3 任务 × 2 模型，trial 数按现场预算并记录实际数）；加打乱句序对照；记录生成与维护工时 | 回放结果表 + 工时记录 |

**交付物**：投影 v1（含头部版本字段）、`statement→node_id` 映射、3 张任务卡（ground truth + primary trap + rubric 版本）、K1/K2 回放结果、生成/维护工时、一页 go/no-go。

**出口（全满足才进第二阶段）**：

- K2 在「答案基本写在文本里」的任务上，primary-trap avoidance 相对 K1 ≥ +5 pp；低于此按 stop condition 3 停，只发命名+单位修复。
- 投影能由描述记录一键重建，映射表覆盖 100% 陈述（抽检 10 条陈述，`node_id` 均可解析）。
- 生成 + 首轮维护工时 ≤ 5 人日（`推测`），即不超过 2 人 × 2 周 sprint 预算的一半；超支则降级为静态投影。

### 客户指标/V3

**受益者与痛点**：一线运维/领域工程师（误诊、重复排障工时）；值班经理/工艺 owner（误设点与越界操作）；知识维护者（教训散在日志、每次回答都要重找）。

| 指标 | 定义 | 当前值怎么拿 |
|---|---|---|
| primary-trap 误判率 | 掉进任务 primary trap 的 trial 比例 | 3 任务回放，先测 K1 基线 |
| element score | 任务要求的关键元素得分 | 同回放，分开报 |
| 误设点事故/千次 | 被安全层拒绝或需人工回滚的写命令比例 | 安全层日志 |
| 排障工时/次 | 从告警到定位根因的工时 | 班组工单抽样 |
| 投影维护人日/月 | 重生成 + 教训并入 + 评审 | curator 工时记录 |
| 投影字符数 / 上下文占比 | 45k 字符占目标模型上下文的比例 | 生成器输出 |

**反事实**：只做 K1 命名+单位；或继续用文档检索/整塔 JSON。N&D 上 K1 已拿到已测各层里最大的一层增益（+54.6 pp），所以「不做投影」不是稻草人，是必须打败的基线。

**试点设计（V3）**：1 台设备、9 任务（5 读数解释 + 4 事故诊断，沿用 N&D 的任务构造法）、K1 vs K2、固定 rubric 版本、预注册主指标与停止线；judge 用两个模型复核，并单独报告 κ 的抽样 trial 数：N&D 两 judge 在 primary-trap 上 κ=0.819（121 trial）可当较强的一致性；作者与 judge κ=0.696 只在 7 个 trial 上算、低于预注册 0.7，不能当强一致性；element score 的 κ 未报。trial 预算按现场算力定，先写进预注册再跑。

**成功 / 失败 / 停止线**（全部 `推测`，客户价值尚未验证）：

- 成功：K2 相对 K1 的 primary-trap avoidance 提升 ≥15 pp，维护 ≤2 人周/月，且安全层拒绝率不因投影上升。
- 失败：提升 <5 pp，或投影 >60k 字符，或维护 >2 人周/月。
- 停止线：`年省工时 × 工时价 + 年减少误设点事故 × 单次成本 < 塔构建摊销 + 投影生成 + 维护`。没有工时价/事故成本就先测分母，不立项。

**为什么只能标 `推测`**：N&D 的收益是 element score 与 trap avoidance，不是客户财务指标；从分数到「省多少工时/少多少事故」的换算没有任何来源。

### 反例

1. **增益可能来自「信息搬进上下文」而非「本体投影」。** K2 比 K1 多的是整份领域描述文本，且任务答案基本写在投影里；JSON 与文本在长度和内容上都不同，是事后描述性比较，GLM-5.2 的 JSON 0.900 还高于文本 0.891。若把现有手册/SOP 直接拼进 prompt 能得到相近分数，塔与投影的构建成本就是纯浪费。**这条不成立的条件**：在同等字符预算下，手工拼接的手册显著低于固定分节投影——本页没有这个实验，必须自己测。
2. **维护成本可能吃掉收益。** 45k 字符/系统，tag/单位/假设/推导任一变更都要重生成；多设备/多站点线性叠加，而 N&D 只测单 plant。维护一旦 >2 人周/月，按 V3 失败线就该停。
3. **顺序敏感说明配方脆弱。** 打乱句序 0.777→0.685，分数依赖叙述顺序；换模型、换语言、换设备类型都要重调顺序，迁移成本未测。45k 字符已接近中型上下文，更长时遵守率是否下降（G1）未知。
4. **工具/检索路线可能更便宜，但成本未测。** 查询工具 0.638、检索 0.597，分数低但天然可追溯；「更便宜」在 digest 里只是可能性（§6.5：论文没有成本对照），token 成本没有数字（`推测`）。若业务只要求可审计而非最高分，投影的边际价值可能不够覆盖构建 + 维护。
5. **单 plant / 9 任务 / 4 模型的外部效度。** 所有 +19.8 pp 都来自一台设备；换到多设备或知识主要靠检索发现的场景，投影增益未被测。连「文本 > 工具」在 Qwen 上都反转过（工具 0.407 < 文档 0.538），排序不是普适规律。
