# 表示：形式化到什么程度

## 问题

同一份领域知识可以用 OWL + 推理机表达，也可以用一份 YAML 约束表达。两者在工程成本上差一到两个数量级，而多数团队在做选择时用的是「哪个更正确」，不是「哪个在当前位置划算」。

## 一条反直觉的立场

**表示形式的选择应由消费位置决定，而不是由语义完备性决定。**

| 消费位置 | 需要的表示能力 | 过度形式的代价 |
|---|---|---|
| 上下文中注入（弱约束） | 自然语言 + 少量结构 | 形式化不产生约束，只占预算 |
| 判定器（强约束） | 可判定的约束、可查询的关系 | 推理不可控时，判定结果无法解释 |
| 记忆状态（中约束） | 槽位与关系的定义 | 过重的模式让状态更新成本过高 |
| 授权判据（最强） | 可由事实查询直接判定的谓词 | 谓词依赖推理链时，授权时延不可接受 |

推论：**先定接缝位置，再定表示。** 反过来做，会得到一个正确但无法消费的本体。

## 形式化的三个档次

| 档次 | 形态 | 适用 |
|---|---|---|
| 词表决 | 概念与关系的清单 | 协作契约、检索增强 |
| 结构表 | 概念 + 关系 + 基数/类型约束 | 判定器、记忆槽位 |
| 逻辑表 | 类公理、可推理的约束 | 需要推导隐含结论的场景 |

绝大多数落地案例停在第二档。第一档常被误认为「已经建了本体」；第三档在实践中常常得不偿失——推理出的结论难以解释，且推理成本不可预测。

## 失效模式

- **形式化被当作目的。** 建了 OWL 文件但没有消费者，最终退化为文档。
- **两种表示并存且不同步。** 自然语言规范与形式化模型各自演化，模型把矛盾的两份都读进上下文。
- **约束仅可读不可执行。** 写在注释里的业务规则，判定器看不见。

## 开放问题

- 第二档能否覆盖大多数判定场景？这一档的边界在哪。
- 能否用同一份源生成两种表示（人读/机判定），从而避免双份不同步？
- 参数的**来源**是否应作为一种关系进入本体？某些工程域已把「参数溯源」显式建模，值得借鉴。
