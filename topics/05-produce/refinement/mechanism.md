# 精化 · 机制

> 只写「它怎么跑」。判断回 [findings](./findings.md)，边界/下一步回 [frontier](./frontier.md)。

## 问题

真实项目很少从零建本体；更常见的是「已经有一个，但不够用/有错/过时」。精化要回答两件事：**该修哪条子类关系/约束**，以及修了之后下游判定器会不会变好；后者目前没有通用答案（F4）。

## 两种做法

| 做法 | 机制 | 代表 | 规模/局限 |
|---|---|---|---|
| 嵌入 + LLM 找高置信修复 | 微调嵌入找候选（30 条可疑公理 × 10 候选父类），LLM 判定，专家复核 | CASTON | 单一本体、6 条高置信修复全部接受；medium 接受率 0–25%（不是全 mixed） |
| 匹配 + 轻量精化 | RAG 检索结构/词法/定义知识，bisimilarity 剪候选，再做轻量精化 | KROMA | 多基准；优于经典与 LLM 基线，开销相当（摘要，`转述` `待核`） |

> KROMA 行只读过摘要（`转述`，`待核`），不作选型依据；只在「跨本体对齐」时作为候选（frontier N1）。

## CASTON 的流程

1. **Candidate generation**：对每条 `A ⊑ B`，用 embedding 给所有候选父类排序；asserted parent 排名很低 → 可疑。
2. 取 top 30 条可疑公理；每条取 top 10 个替代父类。
3. **LLM validation**：给 child/当前父类/候选父类 + label/definition/domain/other axioms；返回 verdict/confidence/替换建议。
4. 只保留 high/medium；专家复核。

**案例（digest §3.2）**：`chromite_sand` 原父类是 `green_sand_molding`（工艺），embedding 把 `foundry_sand`（材料）排在前面；LLM 建议 remove 前者、add 后者，专家 +2/+2；`olivine_sand`、`silica_sand`、`zircon_sand` 有类似结果。`已核`

**数字**：CASTON v1.0.0 270 classes / 306 axioms / 292 条 atomic subsumption；default（fine-tuned OnT + Qwen3-8B）high 6/6（100%）；pretrained ensemble 4/7（57.1%）；GPT-4o mini 5/16（31.3%，该行同时换了 LLM 与 embedding）。medium：default 2/2 mixed；pretrained 1/4（25%）；GPT-4o mini 1/5（20%）——**不是全 mixed**。三个设置合计只产出 40 条 high/medium 建议（40 为论文报数；8 / 11 / 21 按 Table 1 的行数加总）。`已核`

## 核心判断

**CASTON 支持的是「缩候选 + 局部裁决」这个流程，不是「瓶颈在定位与验证」这个因果判断。** 论文把任务拆成两段（292 条 → 30 条可疑 × 10 候选 → 局部裁决），但固定 `k_r`/`k_a` 后只测了池内建议的专家接受率：「定位错」与「验证错」各占多少、真错是否落在池里，都没测。本仓库把「瓶颈在定位/验证」当工作假设（`推测`）：上限更可能在候选召回——真错不在 top-30，或正确父类不在 top-10，后面判得再准也修不到（F5）。CASTON 没把「下游错误 → 该修的公理」闭环（F4）；KROMA 只读过摘要，不能算证据。

## 失效模式

- **只修高置信的小错。** 高置信修的是 6 条局部替换，结构性错误不动；覆盖率未测（F5）。`推测`
- **修了但没测下游。** 本体更「正确」，判定器不一定更好。`已核`（缺口）
- **无回归测试。** 修一条子类关系，可能破坏另一条约束。`推测`
- **来源/版本丢失。** 不知道当前版本是谁改的、为什么改。`推测`
- **medium 不可靠。** default 2/2 mixed、pretrained 1/4、GPT-4o mini 1/5；confidence 只能粗分。`已核`
- **本体层级本身不一致。** 失败案例 `semisolid_metal_(ssm)_processing` 显示，专家都不一致时方法会错。`已核`

## 与本体 / 回路的关系

本体在精化阶段是 **被修改的对象**；约束强度取决于修改后的验证。被违反时通常没有即时信号，需要专家/回归测试。`推测`

## 实施与客户价值（A3/A4）

> 本节引用的分数、条数、参数出自 CASTON digest §3–§4（`已核`；限定：单一本体、单一公理类型、6 条高置信修复；recall@30/@10 未报，见 F5）。人日、阈值、试点判据是本页估算或建议（`推测`），不是论文数字。如果只留一句：**先把「该修哪条」做成可审计的提案队列，别先做自动改写。**

### 实施决策

1. **交付形态选「可疑公理审计队列 + 提案单」，不选自动写回。** CASTON 的 100% 是 6 条高置信替换在 2 位专家 5 分制下都被接受，default 的 medium 2/2 mixed（0 接受）——证据只覆盖「缩小搜索空间后由人裁决」，不覆盖「自动改本体」。这条改变的是上线形态与审批流，不是「要不要修」。
2. **embedding 必须先在本体上 fine-tune；不能 fine-tune 就不要启用 LLM 裁决。** 100%（6/6）vs pretrained ensemble 57.1%（4/7）：同 LLM 下只换 embedding，pretrained 的 7 条 high 里有 3 条被两位专家同时判负，专家会把时间花在否决上（`推测`）。pretrained 只留作对照，不做生产配置。不能 fine-tune（无 GPU/无数据/许可问题）时退回结构检查 + 专家抽审。
3. **confidence 只做分诊，不做自动尺度；换模型/embedding 必须重测校准。** high 进快速复核，medium 一律人审。同一 high 标签换了模型就不可比：固定 pretrained ensemble 时 Qwen3-8B 4/7（57.1%）vs GPT-4o mini 5/16（31.3%），差 25.8 pp，这是干净对照；论文报的 default vs GPT-4o mini 68.7 pp 同时换了 embedding，不能当模型效应。报表要同时看「建议数」：GPT-4o mini 报了 16 条 high，default 只有 6 条——只报接受率会让「少报」看起来更好。
4. **先有回归对，再允许写回。** 修一条 `A ⊑ B` 会改变推理闭包，可能破坏别的约束；CASTON 没测下游，本地必须先有「必须成立/必须不成立」事实对，修复前后各跑一次，diff 无解释不写回（对应 frontier G2）。
5. **第一个阶段不承诺「下游错误 → 该修哪条公理」。** 论文没有闭环（F4 / G1）；先只验证前半段——错误工单能否被可疑清单命中。若命中率近零，精化的立项理由应改为「主动审计」，不是「故障修复」。

### 工程发现 1｜接口：喂什么、吐什么

**输入**：目标本体某一版本的 `A ⊑ B` 全量（CASTON 为 292 条 atomic subsumption / 270 classes / 306 axioms）；每个类的 `id/label/definition/comment/scope note` 与其他公理（即 LLM prompt 的实际字段）；一个能在该本体上 fine-tune 的 embedding 模型（CASTON 用 hyperbolic OnT，适配 EL 本体）。

**LLM 侧判定规则（原文 §3）**：`A ⊑ B` 只有满足「A 的每个实例都必然是 B 的实例」才算正确父类；允许多重继承。这条要写进 prompt，否则 `partial` 会泛滥、提案单里全是「语义相关但不成立」的替换。

**开源实现**：OntRefine（https://github.com/HuiYang1997/OntRefine），可复用候选生成与 prompt 组装（`已核`，digest §10）。

**LLM 输出（JSON，原文 §3）**：`{"concept", "verdict_per_parent": [{"parent", "verdict": correct|incorrect|partial, "confidence": high|medium|low, "reason"}], "suggested_replacements": [{"remove", "add", "reason"}]}`。

**提案单（人审入口，必填字段；本页设计，`推测`）**：`axiom_id, child, current_parent, candidate_parent, embedding_rank, verdict, confidence, reason, expert_score_1, expert_score_2, decision(accept|reject|defer), reviewer, reviewed_at, ontology_version, model_id, embedding_version`。

**写回记录（本页设计，`推测`）**：`change_id, axiom_id, old_parent, new_parent, evidence(提案单 id + 两位专家分), approved_by, version_before/after, rollback_ref`。没有 `model_id` / `embedding_version` 的旧提案不复用——校准是模型特定的，复用等于换了个模型还在用旧阈值。

**回归接口**：`{fact_id, pattern/query, expected: hold|not_hold, scope}`；修复前后各跑一次闭包，输出 `added/removed entailments`。CASTON 未给回归集，字段是本页设计（`推测`）。

**下游对接（第二阶段）**：工单 `{ticket_id, app_query, expected_answer, actual_answer}` → 人工标注「能否指到某条公理」。这是 G1 的标注来源，**不让 LLM 自动归因**。

### 工程发现 2｜参数：k_r=30、k_a=10，但召回没报

- **两阶段参数（原文 §3.1）**：`k_r=30` 条可疑公理、每条 `k_a=10` 个替代父类；候选池排除 A 自身**与所有已断言父类**。
- **截断阈值论文没给**：「asserted parent 排名低」到什么程度算可疑，原文只给 `k_r=30` 这个取值，没给 rank 分布的判据。本厂须自定并写进配置（`推测`），否则「可疑」不可复现。
- **两个召回必须自己测（论文 §3–§4 未报；F5）**：
  - `recall@30`：专家标出的真错公理里，有多少进了前 30 条。这是整条 pipeline 的**定位上限**。
  - `recall@10`：每条真错的正确替代父类，有多少在 10 个候选内。这是**修复上限**。池子排除已断言父类 → 若正确修法是「补一个已断言的父类」，这条不在池内；要单独记「已断言父类命中」，否则 recall@10 会系统性漏计。
- **怎么测**（本页设计，`推测`）：抽 ≥30 条专家已判真错的公理跑一遍排序，报 `命中/总数`；再给每条真错标注正确父类，看是否在 top-10。**没有这两个数，不要用接受率给上线背书**——6/6 只是池内接受率。
- **小本体不适用**：`k_r=30` 在 292 条上是约 10%；本体只有几十条 atomic subsumption 时，30 条已接近全量，缩候选没有收益（见「别用」）。
- **来源**：[CASTON digest](../../../src/papers/2610.21466-caston-refinement/digest.md) §3.1、§4；原文 §3.1–§3.2。

### 工程发现 3｜成本：fine-tune 一次性，专家复核是主项

| 角色（owner） | 负责 | 人日（`推测`） |
|---|---|---|
| 本体 owner | 版本冻结、写回审批、回滚 | 2–3 |
| 领域专家 ×2 | 5 分制盲评 high/medium；仲裁 mixed | default 规模 8 条 × 2 人 × 0.5–2 h ≈ 1–4 |
| ML/平台 | fine-tune、全量排序、LLM 调用与 JSON 校验 | 3–5 |
| 下游应用 owner | 回归对、工单标注 | 1–2 |

**运行成本**：每版本一次全量排序（292 条，轻量）；30 条 × 10 候选 = 300 个待判候选，按每条公理一次调用估算 30 次 LLM 调用/版本（`推测`）；fine-tune 一次性 GPU；专家评审通常是主要成本项（`推测`），且随 high/medium 条数线性增长（default 8 条，GPT-4o mini 21 条）。论文未给 token 单价或 GPU 小时，按本厂算力/单价折算（`推测`）。维护：每本体版本重跑排序与验证，0.5–1 人日/版本（`推测`）。

**关键成本结构**：候选生成便宜、专家复核贵（`推测`，没有任何实测成本）。因此「把 292 条缩到 30 条」本身没有价值，价值在**排序让前几条更可能是真错**。若 top 30 的命中率接近随机，这条 pipeline 只是给专家换了一种抽审方式。

### 工程发现 4｜stop：5 条「别用」+ 运行停止线

#### 别用（digest §6.3 的 5 条，逐条给本地判据）

> 这 5 条是 digest 的工程建议（`推测`；其中「层级不一致」「只做替换」「单本体」有原文依据），不是论文测量出来的边界；本地判据是本页建议。

**用（digest §6.3）**：中等规模本体、能在本体上 fine-tune 的 embedding、2 名可盲评专家，目标是父类替换。`推测`（digest 建议；论文只证明了「单本体、单一公理类型」这一格）

| 别用条件 | 为什么 | 本地判据（`推测`） |
|---|---|---|
| 本体很小 | 缩到 30 条的收益抵不过 fine-tune + pipeline 开销，专家直接过更便宜 | atomic subsumption < 约 100 条 |
| 层级本身不一致 | 失败案例：专家都不一致时方法会错，精化只是给争议加噪声 | 同批 expert mixed > 1/3（见运行 stop 3） |
| 需要关系限制/复杂公理 | 论文只覆盖 asserted atomic subsumption；∃r.B、cardinality、disjointness 是作者 future work | 待修公理里这类占比高 |
| 没有专家 | 接受率与 mixed 都靠 2 位专家盲评；没有专家就无法验证 confidence 校准 | 凑不出 2 名可盲评的领域专家 |
| 大规模跨本体 | fine-tune 绑定单本体，跨本体迁移未测 | 目标 >1 本体或 >1 领域 |

#### 运行 stop（本页建议，`推测`）

1. **不能 fine-tune 到目标本体 → 停 LLM 裁决路径。** 只做结构检查（disjointness/domain-range）+ 专家抽审；pretrained 57.1% 不足以支撑提案队列。
2. **high 分层本地抽检接受率 <4/6 → 停自动提案。** 排序结果降级为「可疑清单」，不再出 verdict/替换建议（本页建议阈值，`推测`：CASTON 的 high 只有 6 条、pretrained 只有 7 条，这个量级上 1 条差异就是 14–17 pp，阈值只能粗设）。
3. **专家 mixed 比例过高（本页建议 >1/3，`推测`）→ 先做层级仲裁。** `semisolid_metal_processing` 类失败说明专家都不一致时方法会错；此时继续跑精化是在给争议加噪声。
4. **回归 diff 出现无法解释的删除/新增蕴含 → 回滚并停写回。** 修一条可能破坏另一条，这是 frontier G2 的硬门。
5. **错误工单→公理命中：20 单内 <2 单能指到具体公理 → 不做故障驱动精化**，只保留审计式用法（`推测` 阈值）。
6. **每版本维护 >2 人日 且 版本节奏 <1 次/季 → 停。** 成本摊不开；不如按需请专家抽审（`推测`）。
7. **经济停止线**：`年省专家工时 × 工时价 < fine-tune + pipeline + 每版本维护` → 停。没有工时价就先测分母，不拍板。
8. **召回先于接受率**：`recall@30` 或 `recall@10` 低于预登记线 → 停提案队列（排序没把真错/正确父类带进来，接受率再高也没用）。`推测`

### 第一个 sprint

**范围**：2 周、1 个本体（CASTON 量级：270 类左右的子类层级，只做 subsumption 一种公理类型）、只出提案不改生产图；1 个可 fine-tune 的 embedding + 1 个 8B 级本地 LLM。

| 天 | 做什么 | 产出 |
|---|---|---|
| D1–2 | 冻结本体版本；导出全部 `A ⊑ B` 与类元数据；从现有判定/查询用例抽 20–30 条「必须成立/不成立」事实对（数量按存量定，`推测`） | 数据快照 + 回归对 v0 |
| D3–5 | fine-tune embedding；全量排序；取 top 30 可疑 × 10 候选；记录 asserted-parent 排名分布 | 候选表 + 排序分布 |
| D6–8 | LLM 逐候选裁决（JSON）；只保留 high/medium；同批跑一次 pretrained 对照 | 提案单 + 对照表 |
| D9–10 | 2 位专家 5 分制盲评；回归集前后 diff；结算单条成本 | 评分表 + diff + 工时台账 |

**交付物**：提案单（含 reject/defer 理由）、专家评分表、fine-tuned vs pretrained 对照、回归对 v0 与 diff、工时/算力台账、一页 go/no-go。

**出口（全满足才进第二阶段）**：

- high 抽检接受率 ≥5/6（对齐 CASTON 的 6/6 量级，不是等价；本页建议，`推测`）；
- medium 100% 经人审并有结论，不准自动通过；
- 回归 diff 每条可解释，或已回滚；
- 单条提案的全成本（GPU + LLM + 专家）可算；
- `recall@30` 与 `recall@10` 有本厂数，且与接受率分开报；
- 分档：正好 4/6 → 修一轮再测，不进第二阶段；≤3/6 或任一条件不满足 → 只输出「保留可疑清单、不做提案队列」的结论，不硬上。

### 客户指标/V3

**受益者与痛点**：本体维护者/知识工程师（不知道从哪开始审，只能全量过）；领域专家（审本体是纯支出，「改哪条」没有依据）；下游判定器/应用 owner（错误以线上故障出现，再人工回溯到公理）；审计/合规（变更缺「谁改、为什么、影响什么」的记录）。

| 指标 | 定义 | 怎么拿 |
|---|---|---|
| 真错发现数/10 人时 | 专家判为真错的条数 ÷ 复核工时 × 10 | sprint 台账 |
| high 接受率 | 两位专家都给正的 high 提案比例 | 5 分制盲评（CASTON 为 −2…+2） |
| 提案采纳率 | accept ÷ 提案总数 | 提案单 |
| 回归破坏数/版本 | 修复后新增的失败事实对 | 回归 diff |
| 工单→公理命中率 | 20 单里能指到具体公理的比例 | 第二阶段标注 |
| recall@30 / recall@10 | 真错公理进 top-30 的比例 / 正确父类在 top-10 的比例 | 真错全集上跑排序（工程发现 2） |
| 变更可追溯率 | 有 evidence + reviewer + version + rollback_ref 的修改比例 | 写回记录 |
| 单条提案成本 | (GPU + LLM + 专家人日) ÷ 提案数 | 台账 |

**反事实**：不做 pipeline → 专家在同一预算下凭经验抽 30 条（这是必须打败的基线，不是「什么都不做」）；只做结构检查 → 抓不到父类语义错位（`chromite_sand` 从工艺改材料这类），但成本近零。论文没有下游收益数字，任何「判定器变好」的说法都是 `推测`。

**试点（V3）**：1 本体、2 专家、30 条可疑公理、固定评分表；主指标 = 真错发现数/10 人时，次指标 = high 接受率与回归破坏数；对照 = 同预算专家盲抽。主指标与停止线先写进预注册再跑。

**成功 / 失败 / 停止线**（全部 `推测`，客户价值尚未验证）：

- 成功：真错发现数/10 人时 ≥ 盲抽基线的 1.5 倍（本页建议），high 接受率 ≥5/6，回归破坏为 0 或有解释。
- 失败：high 接受率 <4/6，或命中率 ≤ 盲抽基线，或 mixed 过多导致无法裁决。
- 停止线：`年省专家工时 × 工时价 + 年减少下游误判 × 单次成本 < fine-tune + pipeline + 每版本维护`；分母（工时价/误判成本）没有就先测分母。

**为什么只能标 `推测`**：CASTON 的收益是「专家接受提案」，不是客户财务指标；从接受率到「省多少工时/少多少事故」的换算没有任何来源。

### 反例

1. **6/6 的 100% 不能当方法可靠度。** 双侧 95% 置信下界只有约 0.54（按二项分布算，非论文数字）；且 default 100%（6/6）与 pretrained 57.1%（4/7）只差 2 条提案。把 42.9 pp 当「fine-tune 效应量」会高估收益；若本厂 top 30 里真错只有 2–3 条，排序价值接近噪声。
2. **接受率是专家共识，不是真值。** 5 分制打分主观（`推测`）；失败案例显示专家自己都不一致（`semisolid_metal_processing`，0/−2）。mixed 高时，接受率反映的是「专家是否容易达成一致」，不是「修复是否正确」——此时该停精化、先做层级仲裁。
3. **下游可能根本不受影响。** 修复只改一条 `A ⊑ B`，推理闭包可能不变，或应用不查询该分支；CASTON 没测下游，所以「本体更正确 → 判定器更好」是 `推测`。下游指标不动时，这项投入只能记为审计/合规收益。
4. **维护与迁移成本可能吃掉收益。** fine-tune 绑定单一本体，跨本体迁移成本未测（G4）；本体版本频繁时每版都要重跑。一个本体一年只改两次，专家抽审更便宜（`推测`）。
5. **换模型/embedding 会换掉整套分诊规则。** 固定 pretrained ensemble、只换 LLM：Qwen3-8B 4/7（57.1%）vs GPT-4o mini 5/16（31.3%），且后者报出 16 条 high（default 6 条）——同一 confidence 标签跨模型不可比。论文报的 default↔GPT-4o mini 68.7 pp 同时换了 embedding，不能拆。任何「我们也有 confidence」的复用都要重测校准。
6. **匹配路线可能更便宜。** 若目标是跨本体对齐而非单本体纠错，CASTON 的两阶段不适用；KROMA 摘要声称「优于经典与 LLM 基线、开销相当」，但本仓库只读过摘要（`转述`，`待核`），不足以作为选型依据。
7. **接受率高可能只是分母小。** 6/6、4/7 的分母都是「LLM 判为 high、进入评审的建议」；真错若不在 top-30、或正确父类不在 top-10，根本不会进分母（F5）。只报接受率，会把「没找到」说成「没修错」。
