# 4. 边界与反例：外部信号不是 E

> 本章回答：04 能引用什么、不能证明什么。 ｜ 读完你应该能：在评审时把“厂商/论文说”降级成“信号”，并指出还缺哪一步。

## 4.1 先分清三种材料

| 材料 | 能当什么 | 不能当什么 |
|---|---|---|
| 本仓库 E-xx | 有出处、有限定的判断 | 独立复现（本仓库没有） |
| 已入库 digest（E-21/E-22 的出处） | 一手原文/代码的消化；可回指 | 跨域效应量；部署结论 |
| 未入库 arXiv/预印本 | 机制与单点数字的**信号**；可进候选 | 跨域效应量；部署结论 |
| 厂商指南/博客/Gartner 转述 | 行业在关心什么的**信号** | 效果证明；采购依据 |

> 04 的 `evidence/` 只列“未入库/摘要级”来源；已入库来源通过 E-21/E-22 引用，**不把 signal 写成 E**。

## 4.2 十条边界

1. **LLM 自动建本体没有解决。** 本轮没有 in-scope 的公理识别 benchmark；04 只保留“候选 + 人审”的工程结论，不引 2025 的 F1 数字。
2. **本体评估的 LLM 也不是权威。** 本轮没有 in-scope 的 CQ 评估来源；不引 2025 的 1,393 CQ 数字。
3. **Text-to-SPARQL 的 benchmark 不等于部署。** GGC 是单 KG/单骨干、NLKGQ 是单 snapshot、KGVoyager 是 4 个小型 benchmark；三者没有头对头。SchemaForge +11.50pp 是旧 signal，不引。
4. **OBDA 不等于自然语言查询。** R11 是“本体+映射→SQL”；Text2SPARQL 是“问题→SPARQL”。两者都叫 query，但工程面不同。
5. **访问控制不等于授权。** 标签/分类（Glyph）、策略（无来源）、执行（trustgraph 读路径）是三层；读路径过滤只做可见性，不等于写授权。
6. **语义层指南不等于效果。** AWS/Gartner/厂商指南给架构与词汇，不给对照实验；不能拿它证明“上了语义层就更准”。
7. **来源/时效/授权不是可选字段。** 没有 provenance、temporal validity、authorization，审计与回滚都做不了。
8. **失败会沿图/工具/记忆传播。** 一个抽取错误可能变成 retrieved evidence，再改变控制决策；单点准确率看不见这条链。
9. **单域/单语言/单模型不能外推。** 法律、工业、医疗、建筑的 schema 与法规差异很大；跨域要重测。
10. **成本/组织没有实测。** 厂商说 LLM 分类 token 成本随数据量增长；但没有你的单价/工时/维护数据，不能出 ROI 点估计。

## 4.3 反模式

1. **先建整座本体，再找消费者。** 没有 CQ/负例/消费者，建出来的东西无法验收。
2. **把 LLM 生成的类/公理直接接受。** 候选必须有人审、负例、版本。
3. **把 Text2SPARQL 的 execution accuracy 当业务正确率。** 查询执行对，不等于答案对。
4. **把读路径过滤当写授权。** 看得见 ≠ 写得了。
5. **把厂商架构图当实现。** 没有接口、失败行为、测试，只是概念。
6. **只做输入侧约束，不做输出校验。** 这是“非对称耦合”的典型：输入拦了，输出仍可能错。
7. **没有审计存储就上治理。** 事后答不出“谁、何时、基于哪条证据”。
8. **用单点 benchmark 立项。** 先问：我的域、我的 schema、我的查询分布是否同分布。

## 4.4 什么会改变这些边界

- 出现跨域、跨 schema 的 Text2SPARQL 对照；
- 出现 ontology engineering 的独立复现（不是单 benchmark）；
- 出现真实部署的 false-veto/false-defer/权限审计数据；
- 出现第二个独立语义层实现，且给出效果量与失败行为。
