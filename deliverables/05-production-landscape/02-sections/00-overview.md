# 0. 一页答案：本体落地到底到哪了

> 本页是 05 的正文第 0 章。索引见 [README](../README.md)；证据台账见 [06 案例](./06-cases.md)；边界见 [08](./08-boundaries.md)。

## 0.1 先看一个真实问题

某券商要回答一个看起来很简单的问题：**“按 2026 年某月末的客户资产层级分组，回看各月融资利率变化，解释异常波动。”**

困难不在 SQL，而在四个“同一个词、不同意思”：

- “客户”按哪个时点分层？月末、开户时、还是历史月末？
- “资产”含不含未成交委托、含不含信用账户？
- “融资利率”是合同利率、实际计息利率，还是加权平均？
- 历史月份要不要沿用同一分组？

指标平台有定义，元数据平台有字段，血缘系统有关系，业务解释散在文档和人的经验里。**智能体找到了表，也可能不知道口径、码值、适用条件**——查询能执行，不等于业务问题被回答。这不是假设，是中泰证券在 CCSA TC601 WG15 案例里描述的现场（[来源卡](../../../src/web/modb-2026-zhongtai-ontology/modb-2026-zhongtai-ontology.card.md)）。

05 要回答的就是：**这样的东西，业界到底谁在跑、跑到什么规模、靠不靠谱、有没有证据。**

## 0.2 四条判断

四条判断对应上面的问题链：①形态（谁在跑）→ ②失败（坑在哪）→ ③国别（证据为什么不对称）→ ④成本（钱花在哪）；第 0.5 节给「所以今天该怎么做」。

### 判断一：生产里跑的是「底座 + 薄本体/语义层」，不是自建本体塔（已核·公开证据选择）

**先看证据配比**：8 条 admitted/probation 里，真正是 OWL/对象本体的只有 **Netflix**（领域专用、自建图存储）；中泰是治理语义层已生产、**业务本体在试点**；Snowflake / Sigma 是 **BI 语义层**；**Apple Glyph 是数据目录上的 275 叶治理标签本体**（3.4M 列/98,000 表）；百度 CoeusBI 与联通 UniDataAgent 是 **BI/报表语义层**。所以「**企业级通用本体**在生产、有 A 类证据」的是 **0 条**；「领域专用本体」1 条；「本体试点」1 条；「标签/报表语义层」5 条。把语义层落地读成本体落地，会高估现状。

公开可核的 2026 案例，绝大多数长在已有底座上：

| 案例 | 底座 | 本体/语义层 | 规模 |
|---|---|---|---|
| 中泰证券 | 指标/元数据/血缘治理资产 + 自研 DataAgent | 治理语义层（指标五要素、同义词、口径） | 9,137 知识目录、6,503 指标文档、2,622 表、12 万+ 血缘 |
| Snowflake | 数仓/BI | semantic views（metrics/dimensions/AI metadata） | 5,600 员工、320,000 查询/月（2025-07） |
| Sigma | dbt + Dagster + 仓库 | semantic models（SQL/Jinja 版本化） | 2,883 模型、63 job、6 region |
| Netflix（例外） | 自建 QuipuDB + W3C 栈 | OWL/SHACL/SPARQL 可观测性本体 | 49,000 目录；2B 请求/日；38M 日志/秒 |
| **Apple Glyph** | 数据目录（Iceberg/RDBMS/Cassandra） | 275 叶治理标签本体（敏感性分类） | 3.4M 列 / 98,000 表 / 4 业务线；6 周 ~24,000 条 steward 判定 |
| 京东（signal，公司自报） | 自建商品知识生产 | 数百亿 SKU 商品本体 | 关系建模未规模化；线上失败；SFT 遗忘 |
| 阿里云（C） | PolarDB / Context0 | 数据库内嵌本体（类型≤100、关系≤300） | 产品能力，未见生产客户数 |

> 表里后两行只作边界：京东是 signal、阿里是 C，都**不进**判断一；前五条才是证据（Apple 的 `admitted` 依据见 [06.1](./06-cases.md#61-主台账) 与 [Glyph digest](../../../src/papers/2609.10430-glyph/digest.md)）。完整台账见 [06.1](./06-cases.md#61-主台账)；本节只做摘要。

**没有找到“从零自建通用本体基础设施”的公开成功案例。** Netflix 是例外：它自建了 QuipuDB，但那是**领域专用图存储**，不是通用本体平台，且没有成本数。这不等于“从零建”不存在，只等于公开证据里没有；它支持“先找底座”这个**默认动作**，但“业界默认路线”本身是 `推测`（公开案例选择，不是行业普查）。

### 判断二：复盘里的主诉是语义定义与权限，不是图引擎性能（已核·多案例工程报告）

生产复盘里的坑，几乎都不是“图查询太慢”：

- **影子实体**：厂商演示“数据库表一键转实体”，源表一变，实体全错且没人知道（中泰）。
- **口径漂移**：同一个指标有全角/半角两个版本、同名不同源；报表对不上，模型更对不上（中泰）。
- **权限旁路**：权限按人特批、库级账号绕过用户级行列权限；聚合结果的小桶仍能定位到个人（中泰）。
- **语义视图延迟**：把 semantic view 指向多张十亿行原始事件表，每次提问都 crawl/join（Snowflake）。
- **预聚合维护爆炸**：为每个 dashboard 建 Dynamic Tables，覆盖一扩，管线就维护不动（Snowflake）。

**结论**：验收要先查语义定义、版本、权限、证据链；不要用图数据库 benchmark 代替（E-29）。七种坑落在哪五道关，见 [06 §6.1c 的失败形态图](./06-cases.md#61c-失败形态清单公开复盘里到底摔在哪)。

### 判断三：美国公开证据强在语义层，中国强在平台与单点实践——但这是“证据不对称”（已核·证据基座 / 推测·成熟度）

- **美国**：Snowflake（内部 context layer，5,600 人/320k 查询）、Sigma（2,883 模型）、dbt/AtScale/Snowflake 生态，公开写作给出规模与失败；Palantir 2026 公告给出 Foundry/Ontology/AIP 的客户名单。
- **中国**：阿里云有完整的产品化本体平台（PolarDB 本体知识平台、Context0，2026-09/10 文档）；蚂蚁 TuGraph（2026-05 push）、腾讯 Topbase（2025-12）有图底座/内部大规模图谱，但都在窗口外、只作背景；中泰证券有 2026-09/10 的会议+标准工作组案例；五平台之外还有**小红书 DIBP**（2026-10 QCon：覆盖 80%+ 员工、周活 8,800+，议题摘要、B）；**百度内部**有 CoeusBI（VLDB 2026，A：数千用户/日，生产集 EX 6.03%→23.49%，语义层从查询自动生成）。**五家大厂平台 2026-06 后具名客户 = 0**；三家农商行的客户自述与 50–180 万的银行/央企采购，落在 HugeGraph/NebulaGraph/Neo4j 与海致/星环/金山云等厂商身上。所以“大厂有平台”不等于“大厂有客户”；2026-06 后**大厂外部采用、成本、失败**的独立公开材料仍然很少。

**这是公开证据的描述，不是“美国更成熟/中国更落后”的排序。** 中国材料受公开意愿、语言、渠道影响；不能把“没公开”读成“没做”（E-30）。

### 判断四：成本拐点降的是“建”的门槛，不是“养”的成本（推测）

LLM 让候选 schema、抽取、摘要、别名、问法生成变便宜：阿里 Context0 可以“样本发现”生成候选本体；中泰用 LLM 补业务摘要/别名/问法。

但真正的重活没有消失：

- 中泰：6,503 个指标文档、9,137 份知识目录、12 万+ 血缘、7,000+ 同义词；LLM 只做解释，技术事实由程序整理，解释必须过来源证据核验。
- Snowflake：语义层要版本控制、peer review、CI/CD、eval、materialization。
- Sigma：2,883 个模型、63 个 job、6 个 region 持续 build/deploy。

**所以“成本拐点”是 `推测`：启动成本降了，定义治理/维护成本没降；公开材料没有全生命周期账本（人月/年维护/回收期），只有两条客户自述的投入量级**（江西农商 <50 万上限、江南农商 3 人×12 月）（E-31）。

## 0.3 一页地图

```
应用层        Agent / BI / 风控 / 运维 / 客服
                 ↑ 用同一套定义
语义层        本体 / 指标 / 同义词 / 权限 / 版本 / 证据
                 ↑ 长在所选底座上
底座/载体层   可多选，可并存：
              数仓语义层（Snowflake/dbt/Sigma）
              本体平台（Palantir/Stardog/Ontotext）
              图数据库/GraphRAG（Neo4j/蚂蚁 TuGraph）
              数据库内嵌（阿里 PolarDB/Context0）
              Wiki/OKF（Markdown + YAML；低成本、LLM 友好；可长期）
                 ↑
数据/治理层    表 / 文档 / 血缘 / 质量规则 / 权限
```

图见 [02 地图](./02-map.md) 与 [`_figures/landscape-stack.svg`](../_figures/landscape-stack.svg)（若预览器不解析，直接打开文件）。

**底座不是单选题**：数仓语义层、本体平台、图数据库、数据库内嵌、Wiki/OKF 是五种常见**载体**，可以单选，也可以同时用几个（例如数仓语义层做指标口径、Wiki/OKF 做概念与文档）。Wiki/OKF 只是其中一种；它成本低、对 LLM 友好，可以长期用；出现跨页关系查询、约束/权限要执行时再另建本体/语义层（OKF 不会自动升级，见 4b.5）；不是所有团队都走它。详见 [4b](./04b-okf-wiki.md)。

**读法**：先问“底座是什么”，再问“本体做多薄”，最后问“谁负责口径/权限/退役”。不要反过来先选本体语言。

## 0.4 证据天花板

| 等级 | 是什么 | 能撑什么 | 不能撑什么 |
|---|---|---|---|
| **A / admitted** | 一手工程复盘/公司生产报告，披露规模 + 失败/限制，有独立信号 | “某形态在某规模下可行/失败长什么样” | 跨行业推广、ROI |
| **B / 具名采用** | 具名组织在生产中使用，有独立信号 | “有人在投、在跑” | 效果、成本 |
| **C / 厂商材料** | 产品页、白皮书、赞助调查、二手转述 | 只作线索，用来找 A/B | 任何结论 |

本份有 **8 条 admitted/probation**（中泰×2、Snowflake、Sigma、Netflix、Apple Glyph、百度 CoeusBI、联通 UniDataAgent），15+ 条 C/signal 类线索；没有一条同时披露“规模 + 成本 + 失败 + 独立印证”。逐项对照图见 [06 §6.1](./06-cases.md#61-主台账)。所以：

- **能回答**：谁在跑、什么形态、公开规模、失败长什么样、哪类证据缺。
- **不能回答**：哪家平台最好、ROI 多少、跨行业能不能复制、成功率多少。

## 0.5 如果你只记三件事

1. **不要从零建本体塔**：先找底座（数仓语义层/本体平台/图库/数据库内嵌/Wiki·OKF），再从最痛的一个口径域做薄本体。
2. **预算给“养”而不是“建”**：语义 owner、同义词/口径版本、权限计算、退役机制；LLM 只帮你建，不帮你养。
3. **用证据等级读厂商**：产品页/客户案例默认 C；要问“有没有具名生产参考，披露规模、成本和失败”。没有，就只当线索。
