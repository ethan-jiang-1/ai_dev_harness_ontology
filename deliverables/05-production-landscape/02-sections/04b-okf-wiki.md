# 4b. Wiki/OKF：底座选项之一，可以长期用

> 本页回答：直接上完整本体太贵，Wiki/OKF 能不能作为一条更便宜的路？它可以长期用，还是只在某些阶段用？ ｜ 读完你能：判断你的场景该停在 OKF、长期并行，还是升级到本体/语义层。
>
> **先说结论**：OKF/Wiki 是**底座选项之一**，不是必经阶段；它可以长期并行，也可以按需升级。OKF 是 Google 的开放知识格式（v0.1 2026-06-12，v0.2 2026-07-24；[卡](../../../src/web/google-okf/google-okf.card.md)），把 Karpathy 的 LLM Wiki 模式形式化；它把“知识可读、可审、可版本化、可溯源”做便宜了，而且正好用上 LLM 的读写/记账能力；执行侧的约束/权限要另接。把它当知识层/前置层可以；把它当“会自动长成语义层”的路径，目前是推测，不是已证。

## 4b.1 它解决什么问题

不要先问“它算不算本体”，先问“它把哪段成本降下来了”。OKF 的价值在三件事：

1. **生产成本低**：一份 Markdown 就是一个 concept；不需要 SDK/runtime，git 就能版本化；人可读、agent 可读，改一处不用动整套系统。
2. **对 LLM 友好**：concept 一文件、frontmatter 少量结构化字段、链接成图；LLM 可以读、写、补交叉引用、批量改十几个文件——这正好是 Wiki 最容易烂掉、而 LLM 最擅长的记账工作。
3. **可逐步加严**：v0.2 的 `sources`/`verified`/`status`/`stale_after` 先解决“能不能信”；需要执行约束/权限/跨页关系时，再接语义层/本体。

**边界**：它负责“把知识组织好、让人和 agent 都能用”，不负责执行/约束/权限；这些要语义层/策略引擎。把它当前置层可以，但别指望 Markdown 自己拦动作。

## 4b.2 OKF 到底是什么

| 项 | 内容 |
|---|---|
| **提出者** | Google Cloud（开放规范，Apache-2.0；不是 W3C/ISO 标准） |
| **版本** | v0.1 2026-06-12；v0.2 2026-07-24（加信任信号） |
| **形态** | bundle = 一个目录的 Markdown 文件；一个 concept 一个文件；文件路径就是 concept id |
| **必填** | v0.1 只有 `type`；约定 `title`/`description`/`resource`/`tags`/`timestamp` |
| **图** | concept 之间用普通 Markdown 链接；链接图就是知识图；`index.md` 做渐进披露，`log.md` 做历史 |
| **v0.2 信任信号** | `sources`（来源/作者/使用量/更新时间）、`generated`/`verified`（谁生成、谁独立确认）、`status`/`stale_after`（生命周期/过期）、`attestation`（数值按约定计算） |
| **运行** | 不需要 SDK/runtime；可在 git、Obsidian、Notion、MkDocs、静态文件服务器里读 |

**它解决什么**：知识碎片化、不可移植、不可审、不可版本化、agent 读不到；它让“同一份知识”同时被人读、被 agent 读、被 git 管。
**它不解决什么**：概念/关系的公理语义、约束/基数、推理、查询执行、策略/权限、身份/时点。

> **规范原文的硬证据**（SPEC.md v0.2，2026-11-12 抓取；[卡](../../../src/web/google-okf/google-okf.card.md)）：whole-word 统计全文 **0 次**出现 ontology / RDF / OWL / SHACL / SPARQL / knowledge graph；`semantic layer`（空格）0 次，`Semantic-layer`（连字符）只在 §12.3「Considered and deferred」出现 **1 次**，是 attester 的未来工作目标。non-goals 明确放弃“固定概念类型分类法”“规定存储/服务/查询基础设施”“替代领域 schema”。这不是我们解读，是 Google 自己划的边界。

## 4b.3 中泰的 OKF：中国目前最实的“前置层”落地

中泰证券 2026-10-15 的 CCSA TC601 WG15 案例（[卡](../../../src/web/modb-2026-zhongtai-ontology/modb-2026-zhongtai-ontology.card.md)）明确写：知识载体采用**开放知识格式（OKF）**，参考 Google Cloud 的开放知识格式和 Anthropic 的仓库化知识实践，以**带轻量结构化头部的 Markdown** 保存知识；一份文档既能供人读/审，也能被检索、供 agent 上下文、支持后续 SQL 校验。注意：这是 **Google OKF 的本地化变体**（同时混了 Anthropic 仓库实践），不是 Google 官方客户/认证案例。

它做到了什么：

- **规模**：9,137 份知识目录、6,503 个指标文档、2,622 张可检索表、12 万余条物理血缘。
- **生产分工**：三泳道——字段/公式/血缘等技术事实由程序整理；模型只补业务摘要/别名/常见问法；模型解释必须过来源证据核验；没有依据的语义内容剔除。
- **门禁**：检索依据不足继续查；口径不明向用户澄清；核心字段缺证据返回缺口清单；校验不通过不交付 SQL。
- **演进**：数据领域的治理语义层已在生产；**业务本体仍在信用业务经营分析场景验证**（“已启动业务本体演进探索”），不是全公司本体生产系统。

**这说明**：OKF 当前置层不是纸上谈兵——中泰用它把“指标/元数据/血缘/业务解释”组织成可检索、可追溯的知识，再往业务本体走。**但它也说明**：OKF 只走到“知识可调用”，业务本体（对象/身份/关系）是下一层，还没全面上线。

**第二个中国线索：京东海博（2026-09-24，signal）**。京东本地生活事业部海博团队称采用 OKF 规范建“项目—角色—Skill”三层知识体系：一概念一 Markdown；YAML 头部只有 `type` 必填；保留 `index.md`（渐进披露）与 `log.md`（变更记录）；宽容消费（字段不全/链接失效可降级为普通文档）。AB 实验：用知识库的 AI 需求分析约 **542 秒**，比只给代码的 AI **快约 44%**（967 秒）。它的判断很硬：“瓶颈不在运行时检索，而在知识生产、结构化、关联维护与生命周期管理”，所以把编译从运行时前移到维护期。**局限**：单一来源、无个人署名、无成本/失败率；**原文 5 次写“OKF”但从未展开缩写，“= Google OKF”是推断**；780+ 商家/10 万+ 门店是 SaaS 业务规模，不是知识库规模。

## 4b.4 Google 的下一跳：OKF → Knowledge Catalog

Google 2026-08-26 的博客（[原文](https://cloud.google.com/blog/products/data-analytics/scale-okf-bundles-across-an-organization-with-knowledge-catalog)）给了 OKF 的“组织级”路径：把 OKF bundle push 进 **Knowledge Catalog**，每个 concept 变成一个 Entry，继承 IAM；`index.md` 变成可浏览层级，`okf` Aspect 带 13 个字段（`okf_type`/`generated`/`sources`/`verified`/`status`/`stale_after`/`usage_window`/`runtime`/`parameters`/`computation`/`executor`/`attester`/`extra`——**没有 `attestation` 字段**），可被搜索/过滤/权限控制。

- **它证明**：OKF 可以从“git 里的文件”变成“组织级可治理的目录条目”，不是只能小团队用。
- **它不证明**：客户采用/规模/效果；官方示例 `acme_retail` 是**合成**的美国零售商 bundle（9 个 leaf concept/17 个 Entry），不是客户案例。
- **关键边界**：Knowledge Catalog 给的是**目录/治理/检索**；要约束/推理/执行，还得另接语义层。它把 OKF 接到“数据目录”这一层，不是执行层。

**截至 2026-11-12**：除中泰外，还找到**京东海博**（2026-09-24，自称 OKF + AB 效果数；单一来源、无个人署名、**原文从未展开 OKF 缩写，“= Google OKF”是我们的推断**）；其余未找到第二家**具名组织**把 OKF 跑在生产并披露规模/失败的公开材料。Google 自己给的是格式、工具、示例和目录集成。这个缺口要如实写，不能拿“Google 发布”当“企业采用”。

**生态是“长尾工具热、生产证据空”**：GitHub 搜索 `description: "open knowledge format"` 约 501 个仓库，其中具名工具 449★/185★/108★（检索快照 2026-11-12；star 不算信号）；但**具名企业上线 0 条、A 类生产复盘 0 条**。这说明格式有开发者兴趣，不等于企业落地。

### 4b.4b 反例：Wikibase 是先有本体/数据标准，再把 wiki 架上去

如果只看“Wiki 能长多大”，会漏掉一个关键区别：**结构化 Wiki 之所以能撑住，往往是因为本体/数据标准已经先在了。**

- **Kunstenpunt（Flanders Arts Institute）** 2026-06-02 的 Wikibase 案例（[原文](https://tech-news.wikimedia.de/2026/06/02/kunstenpunt-a-whos-who-of-the-flemish-art-scene/)，作者 Tom Ruette，**与 OKF 无关**）：100 万+ 页面、约 25 万艺术家/艺术工作者/机构、**3 名专职编辑**、购买 professional.wiki 托管、与 Wikidata 双向联邦。失败披露很实：艺术家抗拒刚性结构；**约束只警告不阻断**；志愿者学习曲线陡；跨部门口径要人工对齐。
- 但它的形态是 **Wikibase = RDF/SPARQL 图库**，前面已经有 Flemish 文化参与数据标准 + CIDOC CRM 对齐。它不是“先 wiki、后本体”，而是“**本体驱动的 wiki**”，一步到位。
- SCIMIN 更典型：SCIMIN CRM ontology 先有，wiki 是标注界面，LLM 只做候选标注，专家复核后才能进生产。

**这说明**：Wiki 可以作为本体的“人机界面/编辑层”，但前提是本体/数据标准已经存在；**OKF 不会自己长成 ontology**。如果你想用 OKF 当前置层，最好在 W1 就同时定义“哪些概念/关系会进本体、谁负责、用什么约束”，而不是等文档堆到几万份再回头补。

## 4b.5 从 OKF 到本体：能映射什么、不能映射什么

| OKF 元素 | 可能映射到 | 自动/人审 | 缺什么 |
|---|---|---|---|
| concept 文件 | class 或 individual | 人审判定“类型还是实例” | 身份/时点/同名不同义 |
| `type` | `rdf:type` / class | 半自动 | 类型层级/公理 |
| `tags` | 标签/属性/受控词 | 半自动 | 正式属性域/值域 |
| Markdown links | 关系边 | 半自动（链接语义靠正文） | 关系类型/基数/方向 |
| `sources`/`verified`/`status` | provenance/trust/lifecycle | 可自动 | 业务约束/权限 |
| 正文表格/示例 | 约束候选 | 人审 | SHACL/OWL 形式化、执行 |
| `attestation` | 计算约定 | 人审 | 查询执行/策略 |

**结论**：OKF 能做“概念/术语/来源/owner/版本”的前置层；不能自动变成可执行本体。升级必须补：**形式约束（SHACL/OWL）、查询/推理执行、策略/权限、身份/时点、版本化 schema**。

更具体地说：

- **可自动的只有三副骨架**：concept 身份（文件路径）、标签、来源/时间戳。
- **关系必须人审**：Markdown 链接没有类型，坏链也合法；同一对 concept 之间可能同时存在“属于/依赖/引用”多种语义，机器分不清。
- **六类映射不了**：约束（基数/必须/禁止）、推理、权限（ACL/行列/属性）、执行（查询/策略）、身份（同名不同义）、时点（as-of/有效期）。OKF 规范明确“不得因缺字段/未知 type/坏链拒绝”，也没有 owner/ACL 字段；v0.2 的 trust tier 原文是 “advisory, not access control”。
- **方向不对称**：迁到本体后**不能删 OKF**，否则会丢掉 freshness/attestation 这些本体没有对应物的信号；合理形态是“OKF 留作权威源/写模型，本体做读模型/派生位”（中泰的方向：OKF 继续作权威源与交换格式，图库/对象关系写在后续规划；“写/读模型”是我们的概括）。
- **v0.2 的净效果**：让**不可信的 bundle 可被识别**，没让**错误的知识被拒绝**；conformance 不等于 truth。
- **一个有用的定位**：独立项目 Linked.Archi（2026-07-17）把 OKF 放在 DIKW 的 **Data→Information** 层，可双向投影/上提到 RDF 图；它指出“**关系定型缺口**”正是两层之间的缝——这和我们的映射表一致：OKF 能当“前置捕获层/交换投影/检索上下文/治理字段面”，不能当本体/策略执行点/权威源/审计账本/规模化方案。

## 4b.6 可选升级：W0 → W1 → W2 → W3

| 层 | 形态 | 能做什么 | 典型失败 | 升级信号 |
|---|---|---|---|---|
| **W0** | 纯 Wiki/文档 | 人读、搜索、审阅 | stale、无 owner、口径漂移 | 同一概念多页面；开始要跨页关系 |
| **W1** | OKF/结构化 Markdown | 多消费者读、版本化、来源/信任/新鲜度 | 链接成图但无约束；agent 写库 trust 崩 | 需要约束/权限执行；多 agent 要稳定 schema；跨页关系查询 |
| **W2** | 轻本体/语义层 | 概念/关系/约束/版本/权限；可查询/校验 | 维护成本；影子实体；权限旁路 | 跨系统对象/动作；高价值应用；重型平台 |
| **W3** | 重型本体平台 | 对象/关系/动作/权限/应用一体 | 平台费/实施重/锁定 | 不适合多数团队 |

**可观测的升级信号**（命中 2 条以上再升级）：

1. 同一概念在 ≥3 个页面/文档里重复，且已有两个“官方版本”。
2. 业务问题需要**跨页关系查询**（不是关键词/向量检索）。
3. 约束/权限**必须执行**（不能只在 prompt 里提醒）。
4. ≥2 个 agent/应用需要**同一套稳定 schema**。
5. 维护人时持续上升，而问答质量不升（stale/冲突）。
6. 审计要求“这个数怎么算出来的”可追溯，而 OKF 只有来源/验证信号，没有计算链。

**建议阈值（`推测`，不是实测）**：≥2 跳/反向查询占比 >20%；同一对 `type` 之间出现 ≥2 种语义链接；语料 >10^4 个 concept 文件；出现“必须/禁止”规则且违规会进对外报表；权限要按任职关系计算；≥2 个写者并发时出现重复页；审计要求 as-of 查询。命中两条以上再升级，不要因为“文件多了”就上本体。

**Wiki/OKF 就够、而且可以长期用的场景**：文档/制度/runbook/术语表/来源索引；单团队、低冲突、只读；agent 只需要上下文，不需要执行；或者 OKF 作为“写模型/权威源”，本体只做“读模型/派生位”（中泰的方向；写/读模型是我们的概括）。**没有出现升级信号，就长期停在 W1 是合理选择，不是落后。**

> **读 02 那张图时要带的两条前提**（图是形态示意，讲不了这两件事）：① 它**不按厂商市场份额或成熟度排序**，横向位置只表示“同属底座层”，不代表谁更强；② 图上出现的产品名只证明**该产品存在**，大多是 C 类厂商文档，不能读成“已生产采用”。底座的强弱要看 [3](./03-us.md)／[4](./04-china.md) 的证据台账，不看图的排列。

## 4b.7 三个反例/边界

1. **OKF 不负责执行**：它把“知识可读/可审/可版本化”做便宜了；约束/权限/查询要另接语义层，别指望 Markdown 自己拦。
2. **agent 写库的信任问题**：v0.2 的 `verified` 是信号，不是保证；没有独立 producer/审计，conformance 不等于正确。社区的一个尖锐说法是：**“一个充满编造内容的合规 bundle，和一个经过审计的 bundle，验证结果一样干净。”**
3. **规模不是升级信号**：文件数可以很大，但真正触发升级的是**语义/执行/权限**，不是文件数（本份没有可引用的规模基准）。
4. **格式还很年轻，别当稳定标准**：2026-06 发布后五个月两次搬家（`knowledge-catalog/okf/` 冻结 → `GoogleCloudPlatform/open-knowledge-format` → 官方 PR #63 指向中立组织，但目标仓库 2026-11-12 实测 **404**）；**没有 v0.3**（无 tag/release，SPEC 仍是 v0.2）；canonical 仓 main 只有 **6 commits、1 位作者、51 个 open issue**（2026-11-12 抓取），main 最新 commit 是 **2026-08-21**。采用前要锁定版本/镜像，不要把“Google 发布”当“长期治理已稳”。

> **标准提醒**：Google 是公司，不是标准组织；OKF 是开放规范，不是 W3C/ISO 标准。引用时写“Google OKF”，不要写“行业标准”。

## 4b.8 给读者的三句话

1. **把 OKF 当底座选项之一**：统一概念/术语/来源/owner/版本，让同一份知识被人和 agent 共读；这比一上来建本体塔便宜得多。它可以长期用，也可以按需升级；不是每个团队都必须走。
2. **用“升级信号”而不是“感觉”决定要不要上本体**：跨页关系查询、约束/权限要执行、多 agent 共用稳定 schema、维护成本超阈值——命中两条，再上本体/语义层；不命中，就长期用 OKF。
3. **把 OKF 的价值讲清楚**：成本低、LLM 友好、可版本化；厂商说“支持 OKF/Markdown”只证明它能装知识，不证明它能执行语义；能用 OKF 长期解决的场景，不必为了“架构正确”强上本体。
