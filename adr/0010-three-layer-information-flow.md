# ADR 0010：三层信息流——src 给 Agent、topics 给 Agent+人、deliverables 给人

- 日期：2026-11-10
- 状态：接受

## 背景

仓库有三层：`src/`（原文/代码/材料）、`topics/`（判断与对照）、`deliverables/`（成品）。三层都能读，但**读者不是同一个人**：

- `src/` 的 digest 是给下游 Agent 取事实、锚点、条件的；写成面向人的长文，检索和复用都会变差。
- `topics/` 是判断台：Agent 要查，人也要能查；但它不是最终文案。
- `deliverables/` 是给人的成品：读者带着任务来，需要通俗、按问题组织、能照着做；不应该要求读者先去 `topics/` 拼一遍。

过去交付物经常在正文里链 `topics/`（“完整矩阵见……”“详细判据见……”），结果读者被送回研究底稿，成品不自包含，三层界限也模糊。

## 决策

三层按**读者**分工，不按“内容深浅”分工：

| 层 | 读者 | 写什么 | 不写什么 | 完成信号 |
|---|---|---|---|---|
| `src/` | **Agent** | 干货：思想、工程实践、事实、数字与条件、代码锚、失败模式；digest 自包含 | 面向人的导读、路线图、总结陈词 | Agent 不读原文就能取用一条事实/锚点 |
| `topics/` | **Agent + 人** | 组织话题：findings、compare、mechanism、frontier；把 src 压成判断、对照、边界 | 最终交付文案、通俗导读 | 同一话题的判断/边界/缺口可查 |
| `deliverables/` | **人** | 通俗、按任务组织；把 topics 消化成读者能照着做/判断的文档；细节可链 topics | 让读者自己拼 topics；内部术语堆叠 | 读者不打开 topics 也能完成任务；要细节时知道去哪 |

四条规则：

1. **单向链**：`src` 是原料，`topics` 是加工，`deliverables` 是成品；成品不要求读者回原料。
2. **主路径自包含**：交付物的正文、步骤、验收不能依赖 `topics/` 才能读懂；细节/出处可以链 `topics/`，但要标“可选”。
3. **不新增判断**：交付物只能重述/重组 `topics/` 已有的判断；发现缺口回 `src/` 或 `frontier`。
4. **写法跟着读者走**：
   - `src`：事实包——结论、数字、条件、`file:symbol`、失败模式；少形容词。
   - `topics`：判断台——决定表、对照、边界；可用内部术语，但每页要能独立查。
   - `deliverables`：说明书——读者问题、步骤、产物、验收、卡住怎么办；术语首次出现解释；把 `topics` 的表消化成读者表。

## 备选

**方案 B：三层都写成面向人**。优点是统一；缺点是 `src` 的检索/复用变差，Agent 取事实要读长文。

**方案 C：交付物只做索引，细节全链 topics**。优点是省写作；缺点是成品不自包含，读者被送回研究底稿——这正是本 ADR 要修的问题。

## 后果

- `src/` 的 digest 可以更密、更事实化；不追求“好读”，追求“可取用”。
- `topics/` 可以保留内部术语与证据等级；不追求最终文案。
- `deliverables/` 必须消化：把 `topics` 的矩阵/目录重写成读者能用的表，正文不要求打开 `topics`；仅保留“细节/出处”可选链接。
- 评审交付物时新增一条：**主路径是否自包含？** 如果读者必须打开 `topics/` 才能完成步骤，退回重写。

## 什么会推翻

- `topics/` 自己变成人可直读的成品，交付物只需索引 → 收紧为方案 C。
- Agent 消费 `src/` 的方式变成读面向人的长文 → 重新评估 `src` 的写法。
- 交付物读者被证明就是研究者本人 → 可以放宽“主路径自包含”。
