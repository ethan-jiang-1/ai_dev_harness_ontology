# 以文档为主要交付物，而非代码仓

本仓库要研究的是「本体在 harness 的哪个位置被执行」。这个问题的答案由**机制、成本与失效模式**构成，而不是由可运行的系统构成；一旦把主体做成代码仓，目录会被实现细节占据（模块、接口、依赖），而研究结论会被迫按代码结构而非问题结构组织。

代价是明确的：没有可运行的对照实验，结论最高只能到「已核」（读过一手原文），到不了「已证」（可复现）。因此设置一个例外通道——需要验证性实现时，**实验设计**留在本仓库之外，实现产物也放在本仓库之外，只在文档里留 `EXP-xxx` 指针。

> **2026-11-09 更新**：`experiments/` 目录已删除。本仓库以学习/消化为主，不在仓内维护实验目录；若未来确实需要验证，仍按“仓库外做、只留指针”的原则处理，不恢复目录。

## Considered Options

- **纯代码仓 + 说明文档**：可验证性最强，但目录结构会滑向实现组织，且与「文档为主」的初衷冲突。
- **代码仓 + 文档双轨并列**：两条线会各自演化并逐渐失同步，维护成本高于收益。
- **文档仓 + 外部实验产物**（采用）：保留问题导向的目录结构，同时为可验证性留出窄口。

## Consequences

- 结论默认上限是「已核」，只有复现了外部实验才能升到「已证」。
- 实验编号成为跨仓库的弱链接：实验产物迁移或丢失时，对应结论必须降级。
- 目录可以按研究问题自由增删层，不受代码依赖关系约束。
