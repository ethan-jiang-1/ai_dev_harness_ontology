# GGC：先判断「这条 query 该不该改」，再决定改不改

> 自包含消化：不假设你读过论文或 `card.md`。先讲清 Text-to-SPARQL 的两类错误，再看 Generator–Gate–Corrector 三段怎么分工、98.33% 这个数是在什么口径与条件下得到的、以及它不能说明什么。

## 0. 三句话

1. **它问什么**：LLM 生成的 SPARQL 常常「能跑但语义错」；既然不是所有 query 都需要改，那**什么时候该触发纠错**？
2. **它怎么做**：三段式——Generator 出初始 query，Gate 用 `(问题, 初始 query)` 做二元分类决定是否纠错，Corrector 只对被 Gate 判为高风险的 query 重写；Gate 与 Corrector 都用同一个 Generator 在训练集上的输出离线造标签/样本。
3. **它发现什么**：MCQA（电影域，31,570 题测试集）上 query-level accuracy 从 90.23%（Generator 单跑）升到 98.33%（选择性纠错，默认配置），但**全量纠错只有 92.34%**；选择性纠错的推理时间约 33h，全量纠错约 60h（Table 2, p.6）。

## 1. 它解决什么问题

Text-to-SPARQL 把自然语言问题（NLQ）翻成可执行的 SPARQL，再在 RDF 知识图谱上执行取答案。相比让模型直接吐答案，中间那条 query 可以被检查、被执行、被复现，所以「可验证」是它的卖点。

问题是**可执行 ≠ 正确**。作者在 MCQA 上把 Generator 的错误分了类：3,085 个错例里，语法错 650 个（21.07%），语义错 2,397 个（77.70%），gold SPARQL 本身跑不通 38 个（1.23%）（Table 3, p.7）。语义错的典型形态是查询范围过宽、关系选错、约束漏写、变量绑定错。作者的主张是：这类 query 多数**能跑但返回不相关答案**，所以只看「执行是否报错」的触发器抓不到——注意 Table 3 只给了分类计数，没有单列「语义错里有多少条可执行」（§4.2）。

所以论文的主张不是「换个更强的生成器」，而是**在生成之后加一层风险判定**：把纠错算力集中到高风险样本上，既提高准确率，又避免把本来正确的 query 改坏。

## 2. 术语

| 术语 | 用大白话说 |
|---|---|
| **NLQ** | natural language question，用户问的那句话。 |
| **Text-to-SPARQL** | 把 NLQ 翻成 SPARQL 查询；query 在 KG 上执行后得到答案集。 |
| **KGQA** | knowledge graph question answering，在知识图谱上答题的总任务。 |
| **MCQA** | 本文主实验数据集（Hoang et al. 2024），电影域，建在 iMKG 上。 |
| **iMKG** | MCQA 用的那个 KG，论文写作「基于 Wikidata 和 MovieKG」。**单 KG**。 |
| **label-based SPARQL** | 查询靠 `rdfs:label "starred_actors"` 这类**标签**匹配关系，而不是 Wikidata 的 `wdt:` 直属性；prompt 里明说「不要用 wdt 语法」。 |
| **query-level accuracy** | 主指标：用生成的 query 执行出的答案集，与用 gold query 执行出的答案集**匹配**的比例（论文未写是否严格集合相等）。 |
| **item-level micro P/R/F1** | 把所有题返回的条目汇总后算的精确率/召回/F1；会被答案集特别大的题主导（见 §4.2）。 |
| **Generator / Corrector** | 两个分别微调过的 LLM：前者 NLQ→query，后者 (NLQ, 初始 query)→改后 query。 |
| **Gate** | 二元分类器，输入 `[NLQ; 初始 query]`，输出「需要纠错」的概率，按阈值 τ 判 0/1。 |
| **trigger rate** | 被判为「需要纠错」的样本比例；也就是 Corrector 实际被调用的比例。 |
| **正类** | Gate 的正类 = 「Correction Required」= 初始 query 错。FPR/recall 都按这个定义读。 |
| **W / C** | Corrector 训练集里「Generator 生成的错样本」/「Generator 生成的正确样本」；`W1.0+C0.2` 表示在全部错样本之外，再加相当于训练集总量 20% 的正确样本。 |

## 3. 它怎么做

### 3.1 三段流水线（Fig. 1, p.4；Algorithm 1, p.5）

```
s(0) = G(q)                      # Generator：NLQ → 初始 SPARQL
g    = Gate(q, s(0))             # 二元判定，g ∈ {0,1}
ŝ    = s(0)      if g = 0        # 不改
ŝ    = C(q, s(0)) if g = 1       # 只在这 9.31% 上纠错
```

**Generator 做什么**（§3.3, p.4）：监督微调（SFT）的 LLM，输入 NLQ，目标输出 gold SPARQL；推理时只出 `s(0)`，不判对错。

**Gate 做什么**（§3.4, p.4）：判断 `s(0)` 是否可能错。输入 `x_gate = [q; s(0)]`——**只有问题与初始 query 两段文本，不含执行结果**（默认配置）。输出 `P(g=1|x_gate)`，`g = 1[P ≥ τ]`，默认 τ = 0.5。

**Gate 的训练标签从哪来**（§3.4 p.4、§3.6 p.5）：把训练集里 Generator 生成的初始 query 与 gold query 比对，错则标 `Correction Required`，对则标 `No Correction Required`。注意这是**离线用 gold 造出来的标签**，推理时不需要 gold，但「什么算错」的定义就是 query-level accuracy 的定义（§4.1）。

**Corrector 做什么**（§3.5, p.4）：输入 `(q, s(0))`，目标输出 gold SPARQL；训练目标是「修错的部分、保留对的部分」。

**Corrector 只在哪些 query 上跑**：只跑 Gate 判 `g=1` 的那些。RoBERTa Gate、τ=0.5 时 trigger rate 为 **9.31%**（Table 4, p.8），即 31,570 题测试集里约 2,940 题（31,570 × 9.31%；按 recall 92.11%、FPR 0.31% 反算也是约 2,930）。剩下约 90.7% 的 query 原样输出。

### 3.2 数据、模型与训练

- **数据（MCQA）**：电影域，单 KG（iMKG，论文写作「based on Wikidata and MovieKG」）；训练 119,409 / 验证 15,785 / 测试 31,570 条。每条含 NLQ、question type、topic entity、answer、gold SPARQL。**question type 的具体类别与分布未报告**；iMKG 的 schema 细节（类数、关系数、三元组规模）也**未报告**，只知道查询是 label-based：关系与实体都靠 `rdfs:label` 字符串匹配，prompt 明令不要用 `wdt:` 直属性。补充实验 SciQA：科学域、KG 为 ORKG，2,565 例（1,795/257/513），剔除 43 条跑不通的 gold 后按 470 题评估（p.18）。
- **骨干**：Generator 与 Corrector 都是 `unsloth/Llama-3.2-3B-Instruct`（3,237,063,680 参数，可训练 24,313,586），LoRA r=16 / α=16 / dropout 0，4-bit 量化加载，max len 2048，batch 2 × 梯度累积 4，1 epoch，lr 2e-4，AdamW_8bit，seed 3407（Appendix A, p.12）。
- **Gate**：默认 RoBERTa-base（约 125M），max len 256，batch 8，3 epochs，lr 2e-5，seed 42；对比 SBERT 骨干（all-MiniLM-L6-v2，22.7M）后选 RoBERTa（Appendix A, p.12；Table 4, p.8）。
- **样本量**（Table 6, p.12）：Generator 12,450 条；Gate 88,506 条 × 3 epochs；Corrector 默认 14,418 条（W1.0 的 11,534 + C0.2 的 2,884；2,884 恰为 14,418 的 20%，可反推 C 比例的分母是「加完之后的训练集总量」）。
- **硬件**：单卡 RTX 3090 24GB；Generator / Gate / 默认 Corrector 各约 1–1.5h 训练（Table 6, p.12）。

### 3.3 一个具体例子（Appendix C.1, Table 9, p.14）

问题：「What are the movies that have the same actor as [Wind] and [Maxwell Caulfield] was the lead actor?」

- Generator 把 `Maxwell Caulfield` 写成了关系侧标签（`?rel1 rdfs:label "Maxwell Caulfield"`），把「同演员」结构整个搭错 → query-level 判错（论文没报这条 query 是否可执行）。
- Corrector 把 `starred_actors` 放回关系位置、把 `Maxwell Caulfield` 改成 `?e4 rdfs:label "Maxwell Caulfield"` 的实体约束，与 gold 一致 → 改对。
- 作者用这个例子说明：Corrector 修的不只是语法，还有**实体-关系角色混淆**。

反例在 Appendix C.2（Table 10, p.15）：Generator 本来是对的（`starred_actors` + `has_tags`），Corrector 却把 `starred_actors` 改成 `directed_by`、`has_tags` 改成 `has_genre`，语义从「演过」变成「导过」→ 改坏。这就是为什么需要 Gate。

第三个例子（Appendix C.3, Table 11, p.16）：「Toy Story 3 和 Toy Story 2 的共同编剧是谁」——Generator 把两部电影压进同一个变量、还凭空引入一个未给出的人名；Corrector 原样保留错误。**结构/逻辑组合类错误，这个 Corrector 修不动**。

## 4. 结果：数字与条件

### 4.1 主结果（Table 2, p.6；MCQA 测试集 31,570 题）

| 设置 | Query Acc. (%) | Item P (%) | Item R (%) | Item F1 (%) | 推理（总 / 每题） |
|---|---|---|---|---|---|
| NSMh（IR 基线） | – | 59.20 | 70.06 | 59.44 | – |
| QGG（SP 基线） | – | 11.65 | 25.13 | 12.32 | – |
| Generator-only | **90.23** | 37.96 | 85.76 | 52.63 | ∼30h / ∼3.4s |
| Gen.+Corr.（全量纠错） | **92.34** | 91.62 | 93.43 | 92.51 | ∼60h / ∼6.8s |
| Gen.+Gate+Corr.（选择性，默认） | **98.33** | 99.62 | 98.70 | 99.16 | ∼33h / ∼3.7s |

**口径（这是最关键的一条）**：`Query Acc.` 是 **query-level accuracy**，定义是「生成 query 执行出的答案集」与「gold query 执行出的答案集」的**匹配率**——它既不是「执行成功率」（能跑就算对），也不是「与 gold 字符串相同」。所以一条语法合法、答案集恰好相同的错 query 会被判对；一条语义等价但写法不同的正确 query 也可能被判错（判等细节论文未报告）。按 31,570 × (1−90.23%) ≈ 3,085，与 Table 3 的错例总数 3,085 对上（四舍五入），可确认分母是全测试集。

**90.23 是 Generator 单跑**（不纠错），不是全量纠错；**92.34 才是全量纠错**。**45%** 是选择性纠错相对**全量纠错**的推理时间降幅：∼60h → ∼33h（每题 ∼6.8s → ∼3.7s，33/60 ≈ 0.55）。相对 Generator 单跑则是**增加约 10%**（∼30h → ∼33h，摘要 p.1 与 §1 p.2 分别写了这两个口径）。

### 4.2 错误分布与两个指标为什么不一致（Table 3, p.7）

| 错误类型 | 数量 | 占比 |
|---|---|---|
| 语法错 | 650 | 21.07% |
| 语义错 | 2,397 | 77.70% |
| gold SPARQL 本身错 | 38 | 1.23% |
| 合计 | 3,085 | – |

- 占比分母是 3,085（含 38 条 gold 错）。若只算「Generator 自身错误」3,047，则语法 21.33% / 语义 78.67%；Appendix D.2 的 SciQA 表用的是**排除 gold 错**的口径（Table 13a, p.17 明说）。两处口径不一致，引用占比时要写清分母（已核，按算术核）。
- Generator 的 item precision 只有 37.96% 而 item recall 有 85.76%，同时 query accuracy 高达 90.23%——说明少数错 query 返回了**极大的答案集**（范围过宽），把 micro 汇总的 precision 拉垮。**不能**把 37.96% 读成「每题只有 38% 的答案是对的」（推测，依据是 micro 汇总被大答案集主导；论文在 §4.3 p.8 也把 item 指标的波动归因于「答案集异常大的离群 query」）。
- Table 3 只分「语法/语义/gold 错」，**没有**再报「语义错里有多少条仍可执行」。所以「77.70% 的错是可执行但语义错」是作者的定性主张，表里没有直接对应列（未报告）。

### 4.3 Gate 本身（Table 4, p.8；正类 = 需要纠错）

| Gate 骨干 | Acc. (%) | Prec. (%) | Rec. (%) | F1 (%) | FPR (%) | Trigger (%) |
|---|---|---|---|---|---|---|
| RoBERTa-base（默认） | 98.95 | 97.00 | 92.11 | 94.49 | 0.31 | 9.31 |
| SBERT（all-MiniLM-L6-v2） | 98.32 | 96.45 | 86.03 | 90.94 | 0.34 | 8.74 |

读法：在 31,570 题上，Gate 只把 9.31% 送进 Corrector，就覆盖了 92.11% 的真错例，同时把 0.31% 的正确 query 误送（约 88 题，按 28,485 × 0.31% 反算，论文未给绝对数）。**这个 FPR 是「选择性纠错不会大面积改坏正确 query」的直接机制证据**——但它是 Gate 的性质，不是 Corrector 的性质（见 C.2 反例）。

### 4.4 阈值与消融（Table 5, p.8）

| τ | Acc. (%) | Prec. (%) | Rec. (%) | F1 (%) | FPR (%) | Trigger (%) |
|---|---|---|---|---|---|---|
| 0.25 | 98.89 | 95.98 | 92.57 | 94.24 | 0.42 | 9.45 |
| 0.50 | 98.95 | 97.00 | 92.11 | 94.49 | 0.31 | 9.31 |
| 0.75 | 98.93 | 97.13 | 91.79 | 94.38 | 0.29 | 9.26 |

- 三个阈值之间 F1 只在 94.24–94.49 之间动，trigger rate 只在 9.26–9.45% 之间动。作者据此说 Gate「学到了稳定的失配信号，不依赖阈值精调」。**但只测了 0.25–0.75 三点**，两端（如 0.05 / 0.95）未测；trigger rate 几乎不动也可能意味着打分高度两极（推测）。
- **KG 执行反馈**（Table 5b, p.8）：带反馈时 Gate Acc. 99.36 / F1 96.66，pipeline query acc 98.70 / item F1 99.09；不带反馈时 Gate 98.95 / 94.49，pipeline 98.27 / 97.72。带反馈更好但只差 0.43pp，且要多一次执行，**默认选不带反馈**。
- **Corrector 训练配比**（Table 5c, p.8）：W1.0 → 98.27%；+C0.2 → 98.33%；+C0.5 → 98.63%；+C0.8 → 98.80%。加正确样本不削弱纠错能力，反而略升；但训练成本从 ~1h 涨到 ~5h（Table 6, p.12），所以默认取 C0.2。**注意 98.33 是默认配比（C0.2）的数，不是这套方法的最好数——最好 98.80（C0.8）。**
- 一处对不上：Table 5b 的「不带反馈」行（98.27 / 97.72）与 Table 5c 的「W1.0」行（98.27 / 97.72）数字完全相同，而 Table 2 的默认结果是 98.33 / 99.16（= 5c 的 C0.2 行）。论文没说 5b 两行各自用哪种配比，两个消融因此**无法完全对齐**（数字已核；对应关系 存疑）。

### 4.5 改对 / 改坏：有没有配对（Table 12, p.17）

结论先说：**没有 2×2 的配对转移矩阵**（fixed / damaged / unchanged 的计数），但有**子集级**证据和三个**单例**证据。

| 子集（query-level acc., %） | W1.0 | W1.0+C0.2 | W1.0+C0.5 | W1.0+C0.8 |
|---|---|---|---|---|
| Gate 触发子集（Correction Required） | 89.58 | 92.38 | 93.46 | 95.30 |
| 原本就错（Originally Wrong） | 82.55 | 85.20 | 86.10 | 87.98 |
| 原本就对（Originally Correct） | 99.98 | 99.99 | 99.99 | 99.98 |

- 「原本就对」的 28,485 题在四种配比下最终准确率都是 99.98–99.99%，即**整条流水线**平均只改坏约 3–6 题；但这发生在 Gate 只放 9.31% 进来的前提下。
- 若只看被误送进 Corrector 的正确 query（约 88 题），改坏 3–6 题意味着**条件破坏率约 3–7%**（推测：由 3–6/88 反算，样本极小，只能当量级，不能当率）。
- 单例：C.1 改对、C.2 改坏、C.3 改不动（§3.3）。
- **算术对不上**：用 Table 12 的 C0.2 行反推，总错例 ≈ 3,085 × (1−85.20%) + 约 3 ≈ 460，即总准确率应约 98.54%，而 Table 2 报 98.33%（≈527 错）。差约 64–68 题。要么子集定义与全量口径不同，要么两次实验不是同一配置；论文未解释（存疑）。

### 4.6 第二个数据集（Table 13, p.17–18；SciQA）

- **规模**：SciQA 共 2,565 例（训练 1,795 / 验证 257 / 测试 513），科学域，KG 是 ORKG；其中 43 条 gold SPARQL 在作者环境里跑不通被剔除，**实际评估 470 题**（p.18）。
- **Generator 错误分布**（Table 13a, p.17）：56 条 Generator 侧失败中，语法 14（25.00%）、语义 42（75.00%）——与 MCQA 同向。
- **结果**（Table 13b, p.17）：Generator-only 88.09% → GGC 94.47%，+6.38pp；item F1 93.94% → 98.23%，+4.29pp。
- **但正文 p.18 写的是「80.70% → 91.62%，+10.92pp」和「item F1 → 98.31%」，与 Table 13b 的 88.09/94.47/98.23 不一致**（已核：正文与表两套数；哪套为准 存疑）。引用 SciQA 时以表为准并注明冲突。

### 4.7 空结果与语义错位怎么处理

- **语义错位**：靠 Gate 的监督信号处理——训练标签就是「初始 query 与 gold 的答案集是否一致」，所以语义错位在标签层面被显式定义；但正文没有单独的「语义错位检测率」指标（只有 Gate 的整体 Acc/P/R/F1）。
- **空结果**：**没有任何专门机制，也没有专门测量**。默认配置下 Gate 看不到执行结果（Table 5b 的 without-feedback 是默认）。带反馈的变体只笼统提到「返回结果是否异常（abnormal）」可作特征，未单列空结果、未报空结果样本量或占比（未报告）。谁要是拿这套做生产，空结果需要自己加一条规则或特征。

## 5. 这些数字不能说明什么

1. **不是多域结论。** 主实验只有一个数据集（MCQA）、一个域（电影）、一个 KG（iMKG）。SciQA 只是 470 题的初步补充，且同一骨干、同一套流程，不能算第二个独立基准（作者自己写 "preliminary"）。
2. **不是「query 等价」判定。** 98.33% 是答案集匹配；语义等价但写法不同的正确 query 可能被判错，答案集碰巧相同的错 query 会被判对。判等实现细节未报告。
3. **不是业务正确率。** 没有人工评审、没有下游任务、没有真实用户；「答案集与 gold 一致」离「回答了用户想问的」还有距离。
4. **不是跨模型结论。** 只有一个 3B 骨干、一套 LoRA/4-bit 配置、seed 3407（Generator）/ 42（Gate），无重复实验、无置信区间。98.27 vs 98.33 这类 0.06pp（约 19 题）的差不要解读。
5. **Gate 不是通用的「对错判别器」。** 它的训练标签来自**同一个 Generator 在同一分布上的输出**；换更强/更弱的模型、换 KG，需要重造标签重训（作者明确列为局限）。
6. **天花板不是 100%。** MCQA 有 38 条 gold 错（1.23%），SciQA 剔除 43/513（8.4%）——两个数据集的「可达上限」都低于 100%，跨数据集比较要扣掉这部分。
7. **没有部署证据。** 只有单卡 RTX 3090 的墙钟时间（∼30/33/60h），没有 FLOPs、没有批量并行下的吞吐、没有失败重试成本。「45%」是这套硬件与这批长度分布下的时间比。
8. **三处内部不一致未被解释。** SciQA 正文 vs 表（§4.6）、Table 5b vs 5c 的对应关系（§4.4）、Table 12 与 Table 2 的算术差（§4.5）。这些不影响「Gate 有效」的方向，但影响精确引用。
9. **作者结论 vs 我的推断要分开。** 「Gate 的低 FPR 避免了改坏正确 query」是作者结论且有 Table 4/12 支撑；「换域后 FPR 会保持」是我的推测，无证据；「语义错里多数可执行」是作者主张，表里没有直接列（§4.2）。

## 6. 工程上怎么用

**复刻顺序（别从 Corrector 开始）**

1. **先固化评价口径**：写清 query-level accuracy 是不是答案集严格相等、空结果算不算错、超时怎么算。口径不定，后面所有数都不可比。
2. **造标签**：用你自己的 Generator 在你的训练集上跑一遍，逐题执行生成 query 与 gold query，比对答案集 → 得到「错/对」标签。这是 Gate 与 Corrector 的共同数据源，也是最大的一次性成本（作者列为局限）。
3. **先训 Gate，验 FPR**：Gate 的价值全在「低 FPR + 高 recall」。先在留出集上看 trigger rate 与 FPR 再决定要不要上 Corrector；FPR 高就直接退回规则或人工。
4. **再训 Corrector，混正确样本**：只喂错样本会让它见什么都想改；加 20% 正确样本是成本/效果的折中（98.33% vs 98.80%，训练 1.5h vs 5h）。
5. **默认不要接执行反馈**：多一次执行只换来 0.43pp（98.27→98.70），但延迟与工程复杂度都涨。
6. **记录 Gate 分数**：它是很好的 triage 信号；低于阈值的原样放行，高于阈值的除了自动改，还应留日志供抽检。

**关键参数/接口**

| 项 | 默认值 | 备注 |
|---|---|---|
| τ | 0.5 | 0.25–0.75 内不敏感（Table 5a）；两端未测 |
| Gate 输入 | `[NLQ; 初始 query]`，max 256 token | 拼接后截断，长 SPARQL 可能被截（推测：论文未报截断率） |
| Corrector 配比 | W1.0 + C0.2 | 想再要 0.5pp 就上 C0.8，训练 ×3 |
| 触发率 | 9.31% | 决定 Corrector 的推理预算 |

**何时用 / 何时别用**

- **用**：schema/关系名相对稳定、可以离线造 gold query、query 量大使「全量纠错」太贵、能接受「答案集匹配」这个口径。
- **别用**：ID-based SPARQL（要实体链接与 schema 对齐，作者明说没做）、开放域、拿不到 gold、需要**保证**（这套没有任何 soundness 保证，Gate 是概率分类器）、错误以**逻辑组合**为主（C.3 显示这类修不动）。

## 7. 质量与边界

- **证据类型**：单基准实证 + 消融 + 案例研究（preprint，无同行评审）。
- **强项**：三段分工干净、可复现（prompt 模板与超参全给，Appendix A/B）；消融覆盖 Gate 骨干、阈值、执行反馈、Corrector 配比；有子集级分析（Table 12）和**失败案例**（C.2 改坏、C.3 修不动）——后者比多数「我们方法更好」的论文诚实；成本表给到小时级。
- **主要威胁**：单域单 benchmark、单骨干、单 seed、无方差；Gate 标签由 gold 离线生成，等于把「什么算对」直接灌进分类器；主指标是答案集匹配且判等细节未报告；三处内部数字不一致未解释；无人工评估、无部署。
- **`quality: B` 的理由**：机制清楚、消融完整、数字可核，属于「单基准/单域/有限评估」——按仓库定义正好是 B，不到 A（没有多基准、没有真实部署）。
- **作者自述局限**（Limitations, p.9）：① 主实验只有 MCQA（电影域、label-based SPARQL），跨域/跨 KG/跨 SPARQL 形式/跨骨干的评估有限，SciQA 只算 preliminary，ID-based SPARQL 还需实体链接与 schema 对齐；② Gate 与 Corrector 依赖**特定 Generator 的误差分布**，换更强/更弱模型要重训或适配；③ 造 Gate/Corrector 训练数据要在大训练集上跑一遍 Generator，有额外离线算力成本。伦理段另说：错 query 会给出误导性答案，真实部署需验证、不确定性提示与人工监督；开放域/ID-based KG 还会引入实体链接错误与 KG 偏见。
- **我判断的外推边界**（`推测`）：单域（电影）单 benchmark（MCQA）、单骨干（3B + LoRA + 4-bit）、单 seed（3407/42）、无重复与置信区间 → 不能外推到「任意 KG 上 +9pp」；Gate 的低 FPR 是**分布内**性质，换生成器/换 schema 后要重新量 FPR 再谈收益。
- **引用时必须带上的限定**：MCQA + iMKG 电影域、Llama-3.2-3B-Instruct 单骨干、答案集匹配口径、默认 W1.0+C0.2、Gate 为分布内监督分类器。

## 8. 与仓库判断的关系

- **`execution_form` 我判 `none`（而不是 `context`）。** 理由：Appendix B 的两个 prompt（Table 7/8, p.13）里只有任务描述、NLQ、topic entity、两个 prefix、以及（Corrector）初始 query——**没有任何 schema/本体文本**；KG 的关系名（`starred_actors`、`has_tags` 等）是通过 12,450 条 NLQ→SPARQL 训练对进入模型权重的（参数化），不是上下文供给，也没有被求值/编译。SPARQL 在 KG 上执行属于**数据检索**，不是本体求值（无推理、无 entailment、无约束校验）。若仓库想把「schema 进权重」单列一档，那要新增档位；在现有五档里 `none` 最贴近，`label` 是次选（关系名只当词表），`context` 不成立（没有进 prompt）。`已核`（依据 prompt 原文与训练设定）。
- **与 E-20（本体执行的形态分类）**：GGC **不应计入 `engine`**。E-20 的四种 `engine` 都涉及本体被求值（查询重写、SHACL 求值、校验、编译成 SPARQL）；GGC 只把 SPARQL 当检索语言，正确性由答案集比对定义。它是「执行 ≠ 本体执行」的一个边界样本（`已核`：按定义；判断部分 `推测`）。
- **与 E-03（强制报告本体观察 + 接地等级）**：两者是不同工具，不能互相支持或削弱。E-03 的接地等级是**模型自评、未校准**；GGC 的 Gate 是**监督训练的二元判定器**，分布内接近饱和（98.95% acc / 0.31% FPR，Table 4, p.8）。GGC 提示了一条替代路线（用监督对分类器代替自评），但它既没测接地等级，也没做 OOD/跨生成器测试，**不构成对 E-03 的反驳**（`推测`：它说明「有标签时监督判别可以很准」，而 E-03 的问题恰恰是标签贵）。
- **对 `03/querying` 的 F2 草案**：原句「90.23→98.33%」方向对，但缺三件事——① 口径是**答案集匹配**，不是执行成功率；② 90.23 是 **Generator 单跑**，**全量纠错是 92.34**，98.33 才是选择性；③ 45% 相对**全量纠错**（∼60h→∼33h），相对单跑是 **+10%**。建议措辞：**「GGC 在 MCQA（电影域、iMKG、31,570 题测试集、Llama-3.2-3B-Instruct 单骨干）上把 query-level accuracy（答案集匹配率）从 90.23%（Generator 单跑）提到 98.33%（选择性纠错，默认 W1.0+C0.2），全量纠错只到 92.34%；推理时间 ∼33h vs ∼60h（−45%），比单跑多约 10%。净收益依赖一个分布内监督训练的 Gate（FPR 0.31%、trigger 9.31%），跨生成器/跨 KG/跨 schema 未测。」** 等级：`已核`（数字，Table 2/4/5, p.6–8）/ `推测`（跨域）。
- **对 `03/querying/README.md` 现有边界句的修正**：该页写「GGC 只报 accuracy/overhead，没有『改对 vs 改坏』配对」。准确说法是：**没有 2×2 配对转移矩阵**，但有 Table 12 的子集级准确率（Originally Wrong 85.20%、Originally Correct 99.99%，C0.2）和 C.1/C.2 两个单例（一改对一改坏）。建议把那句改成「无配对矩阵，只有子集级与单例证据」（`已核`）。
- 没有改变任何跨派 E 判断：GGC 只作 `03/querying` 的机制证据与 E-20 的形态边界，**只作边界证据**，不升 conclusions。

## 9. 还没解决 / 下一步

- **配对转移矩阵**：fixed / damaged / unchanged 各多少？按 Gate 分数分桶画一遍，就能回答「阈值该定在哪」而不是只看 F1。
- **跨生成器迁移**：把 3B 换成 7B/API 模型后，Gate 的 FPR 与 recall 掉多少？标签能否用「执行结果 + 弱监督」自动造，成本多高？这是能否工程化的分水岭。
- **跨 KG / ID-based SPARQL**：作者自己说需要实体链接、schema 对齐、关系 grounding——这三件在本仓库属 `03-knowledge` 的供给问题，值得单独看一篇。
- **空结果与超时**：应不应该进 Gate 特征？现在只有「abnormal」这个含糊说法，没有数。
- **结构编辑 vs 整条重写**：C.3 说明逻辑组合错误修不动；作者引的 Text-to-SQL 方向有 clause-level 编辑，SPARQL 上还没试。
- **判等口径**：答案集严格相等会不会把「等价但不同写法」判错？需要人工核多少条才能估这个偏差？
- **成本口径**：45% 是墙钟时间，不是 FLOPs；批量并行、KV cache 复用下的比值未测。
