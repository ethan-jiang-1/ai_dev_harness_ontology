# CoeusBI：把语义层从「人工建模」改成「从查询里自动长出来」

> 自包含消化：不假设读者读过论文或 `card.md`。先讲清企业 BI 问数为什么难，再看百度怎么用「离线视图生成 + 两级 schema linking + 确定性编译」把它跑起来，逐条核 6.03%→23.49%、55.7%、93% 的条件与样本，最后说清它**不能**证明什么。**一句话：这是「语义层可以自动生成」的第一个大厂生产证据——它降的是建模成本，不是治理成本。**

## 0. 三句话

1. **它问什么**：企业 BI 里，手写指标/维度/关系（YAML/LookML）赶不上 schema 变化；JOIN 密集、schema 超宽、方言各异时，LLM 直接写 SQL 又慢又错。能不能**不靠人工建模**，让系统自己把复杂查询拆成简单视图？
2. **它怎么做**：离线用「视图生成 agent」从专家查询 + 执行错误里自动造单视图；在线用两级 schema linking（先选视图、再剪列）把宽 schema 缩到模型能处理的大小；路由 agent 处理多轮对话，最后用确定性编译器生成方言无关 SQL。
3. **它发现什么**：在生产集 BD-Business Line A 上，执行准确率 **6.03% → 23.49%**、JOIN 查询占比 **77.03% → 47.61%**、Easy 查询 **9.21% → 74.29%**；灰度对照 50 名分析师 3 周，实验组平均查询完成时间**降 55.7%**。系统部署在百度数据平台，服务数千用户/日。

## 1. 它解决什么问题

企业 BI 的标准做法是**人工定义语义层**：指标、维度、关系、join path 写成 YAML 或 LookML（Tableau、Power BI、dbt 一类）。这套东西有两个结构性毛病：

- **维护跟不上**：schema 一变，人工建模就得跟；业务线一多，语义层变成长期工程。
- **宽 schema 打不动**：一家公司几百上千张表，NL2SQL 的 schema linking 在「表多、列名怪、join 隐式」时迅速退化。

百度自己的观察（§1）：在他们某业务线的 golden SQL 里，**90.8% 含 JOIN**；JOIN 一多，生成准确率就掉。论文的赌注是：**别让人写语义层，让系统从「专家查询 + 执行错误」里把视图长出来**——视图就是把频繁 join 的表组合固化成单表，查询只面对视图。

## 2. 术语

| 术语 | 用大白话说 |
|---|---|
| **BI（商业智能）** | 企业里用报表/看板回答「这个数是多少」的系统。 |
| **NL2SQL** | 自然语言 → SQL；用户问「上月 DAU」，系统生成 SQL 去查。 |
| **schema linking** | 把问题里的词对到「哪张表、哪一列」；宽 schema 时最容易错。 |
| **JOIN** | 多表按关联键拼接；BI 查询里很常见，也最容易让生成模型出错。 |
| **view（视图）** | 把一组常一起用的表预先拼成一张「逻辑单表」；查询只面对它，不用再写 JOIN。 |
| **EX（execution accuracy）** | 执行结果与标准答案一致的比例；**不等于业务口径正确**。 |
| **灰度对照** | 随机分两组，一组用新系统、一组用旧工具，跑一段时间比指标。 |

## 3. 它怎么做

**离线准备（Offline Preparation）**

1. **视图生成 agent**：从专家历史查询里找 JOIN 频繁的表组合，造候选视图；再用**执行错误反馈**迭代——查询失败/结果不对的错误会被收集成反馈工件，下一轮用来修正视图定义。作者称这**消除了人工语义建模**（这是作者主张，见 §5）。
2. **向量库按业务线建**：每条业务线自己一套 VDB，存「列→视图」「值→列」「领域知识→列」三类映射（C2C / V2C / ALL2C）。

**在线查询（Online Query Processing）**

3. **Word2View**：先把问题路由到候选视图（向量检索），必要时用微调过的粗排模型（如 Ernie-Tiny v2）直接预测；两个检索器并发、谁先出结果用谁，控延迟。
4. **View2Column**：在选中的视图里剪掉无关列，把上下文压到模型能处理的大小。
5. **Routing Agent**：判断这轮是「新问题」还是「改上一轮」；改的话走增量修改（MRD），不重跑整条链路。
6. **确定性 SQL 编译器**：把中间表示编译成方言无关 SQL——这一步把「模型生成 SQL」换成「模型生成表示 + 编译器生成 SQL」，消掉方言与幻觉。

## 4. 结果：数字与条件

| 数字 | 条件（数据/设置/样本） | 它意味着什么 |
|---|---|---|
| **90.8%** | 百度某业务线 golden SQL 里含 JOIN 的比例（§1） | JOIN 是主要矛盾，不是边角 |
| EX **61.67% → 63.40%** | BIRD-dev，DIN-SQL + DeepSeek-R1-0528，加视图前后 | 公开集上只小幅提升（+1.7pp）——视图不是万灵药 |
| EX **6.03% → 23.49%** | **生产集 BD-Business Line A**，同模型，加视图前后 | 生产集提升大（+17.5pp），说明原来 JOIN 把准确率压得很低 |
| JOIN 占比 **77.03% → 47.61%** | 同上 | 视图确实把一半 JOIN 消化掉了 |
| Easy 查询 **9.21% → 74.29%** | 同上 | 大部分查询从「难」变「易」 |
| 平均完成时间 **−55.7%** | 灰度：50 名分析师随机 25/25，3 周，A 组用 CoeusBI、B 组用旧工具 | 唯一带对照的生产端收益数 |
| **93% / 89%** | 灰度用户反馈：schema linking「可靠找到列」/ MRD「像人一样改」 | 主观反馈，不是客观指标 |
| 公开集规模 | MS-Financial-Views 200 表 / 7,400 列 / 37 列每表；MS-Commercial 2,281 / 65,000 / 28.5 | 两个公开集都不算「超宽」，宽 schema 的压力主要在生产集 |

> **读法**：公开集 +1.7pp、生产集 +17.5pp，差距说明**收益取决于原系统有多依赖 JOIN**；不要把 +17.5pp 当成「换任何 BI 都提升这么多」。

## 5. 这些数字不能说明什么

1. **不能外推到别的公司。** 单公司（百度）、单业务线（BD-Business Line A）的生产数字；其它业务线只有「覆盖」的说法，**没有逐条数字**。
2. **EX 不是业务正确率。** 结果集一致 ≠ 口径对；作者没有报人工正确率、没有报错误答案的事故/返工。
3. **没有失败率。** 「数千用户/日」是定性量级，没有 DAU、查询量、失败查询比例、多轮对话的放弃率。
4. **没有美元成本。** token 效率是相对比较；没有账单、没有人月、没有 ROI。
5. **灰度对照有混杂**：25 人一组、3 周、同一批业务线，但**没有报两组的基线差异**（经验、任务难度）；55.7% 是「平均完成时间」的组间差，不是因果估计（作者也没做统计检验）。
6. **「消除人工语义建模」是作者主张**：视图是自动生成的，但**视图质量、覆盖率、错误视图的发现与退役**都没有独立测量；也没有和「人工语义层」做同任务对照。
7. **不是本体。** 这套东西是「视图 + 列」的语义层，没有 OWL 类/公理/约束；不要拿它证明「本体推理有用」。

## 6. 工程上怎么用（本篇主角）

### 6.1 复刻顺序（第一步做什么）

1. **先证明 JOIN 是主要矛盾**：抽一批 golden SQL，统计含 JOIN 比例与失败样本。若 JOIN 占比低（比如 <30%），这套方案收益有限。
2. **从历史查询里挖候选视图**：不需要先建完整语义层；先按「高频表组合」聚类，造 10–30 个单视图。
3. **接错误反馈闭环**：把执行失败/结果不对的样本回灌给视图生成 agent；没有这个闭环，视图会停在第一版。
4. **两级路由**：先「问题→视图」，再「视图→列」；宽 schema 的关键是**先缩表再缩列**，不是把全 schema 塞进 prompt。
5. **把 SQL 生成换成「表示 + 编译器」**：方言与幻觉在编译层消掉，模型只负责中间表示。
6. **灰度验证**：随机分组、跑 2–3 周、只看「完成时间 / 需要人工改的比例」，不要只看离线 EX。

### 6.2 成本与使能

| 成本 | 一次性/每次 | 量级与来源（论文实测 / 工程提议 / 推测） |
|---|---|---|
| 视图生成 | 一次性 + 持续 | 论文没报人月；从「错误反馈迭代」看是持续运行（工程提议：设覆盖率与错误视图退役指标） |
| 在线延迟 | 每次 | 论文报 p50 级；两级检索 + 粗排模型是为控延迟（§5） |
| 粗排模型 | 一次性训练 | Ernie-Tiny v2 一类小模型；论文未报训练成本 |
| 编译层 | 一次性工程 | 确定性编译器，方言无关；论文未报工程量 |

**为什么以前不行、现在行**：

- **能力阈值**：LLM 能稳定产出「视图定义 / 中间表示」这类结构化改写，且能从执行错误里迭代——2026-06 前这条闭环不稳。
- **成本/工具**：向量库 + 小模型粗排把宽 schema 的检索压到可接受延迟；确定性编译器让「模型不碰 SQL 方言」成为可行架构。

## 7. 质量与边界

- **来源**：`admitted`（I1 PVLDB Vol.19 同行评审 + I2 百度/北邮 + I5 官方 artifact）。**生产部署的自述部分仍只有公司一方**。
- **可核性**：数字有表号（Table 1/2、§8.4.4），PDF 在库；但灰度研究**没有附录数据**，55.7% 无法复算。
- **与 10 的分级**：10 把它记为 **A**（有独立信号 I1），与 Snowflake/Sigma 的 A（probation）不同——差别就在「同行评审」这一条。

## 8. 与仓库判断的关系

- **E-28（底座 + 薄本体）**：支持，且加一个新变体——**语义层可以是「从查询里自动长出来的视图层」**，不必先手工建模。它不是「从零自建本体塔」，而是在既有数仓/BI 上加一层自动生成的语义视图。
- **E-29（失败在语义/权限/维护）**：**不并入**。这篇的失败是**消费侧**（JOIN 准确率、宽 schema linking、方言、多轮成本），不是治理侧（影子实体/口径漂移/权限旁路）。把它塞进 E-29 会把两类失败混成一句。
- **E-31（成本拐点降建不降养）**：**支持且加强**。人工语义建模被自动视图生成替代 → 「建」的成本确实降了；但错误反馈闭环、视图退役、灰度验证仍是长期工作 → 「养」没消失。
- **E-30（证据不对称）**：中国侧多一条**大厂内部生产报告**（百度），但**不是外部客户**；五平台外部采用仍然 0。

## 9. 还没解决 / 下一步

- 生产集只有一条业务线：需要其它业务线（或其它公司）的数字才能谈可复制。
- 没有「自动视图 vs 人工语义层」的同任务对照：这是它和人工建模路线之间**最关键、也最缺**的一格。
- 没有成本账本：token 效率不能当钱。
- 视图质量与退役：自动生成的视图会不会变成新一代「影子实体」？论文没测。
