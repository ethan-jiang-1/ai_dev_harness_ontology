# UniDataAgent：先把语义做成版本化契约，再让 agent 出报表

> 自包含消化：不假设读者读过论文或 `card.md`。先讲清企业问报为什么难，再看中国联通怎么把「本体获取」和「报表执行」拆开，逐条核 95.0%/72.5%、「数小时 vs 一周」的条件，最后说清它**不能**证明什么。**一句话：这是中国联通内部的生产证据——本体接地把严格准确率从 72.5% 拉到 95.0%，但样本只有 40 问。**

## 0. 三句话

1. **它问什么**：企业里「问题 → 报表」的自动化，卡点不是 SQL 生成，而是**组织特有的语义**（指标口径、范围、维度、物理映射）。能不能把这些语义做成一份**可复用、可版本化、可审计的契约**？
2. **它怎么做**：拆成离线 **OAV**（从元数据/业务材料/专家技能里生成候选本体 → 用代表性业务问题验证 → 专家评审 → 发布版本）和在线 **QRE**（检索语义契约 → 编排技能与数据工具 → ReAct 循环 → 校验 → 证据链报告）。
3. **它发现什么**：27 张企业表、约数千指标类型下，本体构建从**约一周降到数小时**；40 个真实业务问题上，严格准确率 **95.0% vs 文档 RAG 72.5%**；报告生成从**数个工作日降到几分钟**。

## 1. 它解决什么问题

企业问数系统常见两种失败：

- **只做 SQL**：问题翻译成 SQL 能跑，但指标口径、统计范围、维度归属错了——「数对了，但答的不是那个问题」。
- **只做 RAG**：检索到文档和数字，但拼不出完整覆盖（比如少几个省）、算不出跨指标诊断。

论文的立场：**先把语义做成契约**（本体 + 版本 + 专家评审），在线执行只允许在这份契约里做映射与计算。这是「本体在前、执行在后」的路线，与「让模型自由发挥再校验」相对。

## 2. 术语

| 术语 | 用大白话说 |
|---|---|
| **OAV** | 离线阶段：Ontology Acquisition and Validation，把散落的元数据/业务知识做成版本化本体。 |
| **QRE** | 在线阶段：Question-to-Report Execution，把问题变成带证据的报表。 |
| **语义契约（semantic contract）** | 某个问题该用哪些指标、什么口径、什么范围、什么映射的一份明确约定。 |
| **严格准确率（strict accuracy）** | 答案在结果、范围、条件、口径四项上都对才算对；比「结果集匹配」严。 |
| **ReAct 循环** | 模型「想一步→做一步→看结果」的循环。 |
| **Doc-RAG** | 只检索文档再生成，不预先建本体——本文的对照组。 |

## 3. 它怎么做

**OAV（离线，四阶段循环）**

1. 从元数据、业务材料、专家写的 business skills 里**约束生成**候选本体（概念、指标定义、关系、映射、provenance）。
2. 用**代表性业务问题**验证：问题能不能被这套本体回答、答案对不对。
3. 失败触发**局部修复/重规划**，不是整份重做。
4. 通过验证的候选由**领域专家评审**后发布为版本化本体；后续问题都用这个版本。

**QRE（在线）**

5. 按问题检索对应的**语义契约**（哪些指标、口径、范围）。
6. 编排 business skills 与数据工具，进入 ReAct 循环：计划 → 执行 → 观察 → 修正。
7. 对结果做校验（覆盖、口径、条件），最后生成带**证据引用**的报表。

## 4. 结果：数字与条件

| 数字 | 条件（数据/设置/样本） | 它意味着什么 |
|---|---|---|
| **95.0% vs 72.5%** | 40 个真实业务问题；严格准确率；Ours vs 文档 RAG；DeepSeek-V4 | 本体接地明显优于纯文档检索，但样本只有 40 问 |
| **90.9% / 100% / 100%** | 分任务类型：指标与范围接地 22 问 90.9%（Doc-RAG 81.8%）；完整区域对比 11 问 100%（63.6%）；跨指标诊断 7 问 100%（57.1%） | 增益集中在「需要完整覆盖/跨指标」的任务，不是所有任务 |
| **数小时 vs 约一周** | 本体构建（27 张表、约数千指标类型、数百领域概念、数千语义关系） | 工时是**定性对比**，不是实测人月；「一周」是人工基线 |
| **几分钟 vs 数个工作日** | 单份报表生成 | 同上，定性 |
| **27 张表 / 数千指标类型** | 中国联通某业务域 | 中等规模，不是全企业 |

> **读法**：95.0% 的分母是 40 个问题、单企业；把它当「本体接地能到 95%」会过度外推。真正可迁移的是**流程**（OAV 的验证-修复-评审循环），不是这个百分比。

## 5. 这些数字不能说明什么

1. **不能外推到别的企业。** 单公司（中国联通）、单业务域、27 张表；「可复制」是作者的展望，不是证据。
2. **样本太小。** 40 问、分到三类后每类 7–22 问；没有置信区间、没有重复运行。
3. **工时对比不是人月。** 「数小时 vs 一周」没有说谁在数小时里做了什么（几个人？专家评审算不算？）。
4. **基线只有文档 RAG。** 没有和「人工语义层」「人工建模」做同任务对照——所以不能回答「自动本体比人工本体好吗」。
5. **没有失败率/错误分布。** 95.0% 之外的 2 个问题错在哪、为什么错，没报。
6. **不是通用本体。** 是面向报表任务的语义契约，不是 OWL 公理体系。

## 6. 工程上怎么用（本篇主角）

### 6.1 复刻顺序

1. **先选一个报表域**（27 张表量级），不要全企业铺开。
2. **建 OAV 循环**：候选本体 → 用真实问题验证 → 局部修复 → 专家评审 → 发布版本。关键是「问题即测试集」。
3. **把在线执行约束在契约里**：先检索语义契约，再编排工具；不要让模型自由决定用哪个指标。
4. **加证据链**：每个结论带来源与计算过程，否则报表不可审计。
5. **用「严格准确率」而不是「结果集匹配」验收**：结果、范围、条件、口径四项都对才算对。

### 6.2 成本与使能

| 成本 | 一次性/每次 | 量级与来源 |
|---|---|---|
| 本体构建 | 一次性 + 版本迭代 | 「数小时 vs 约一周」（定性） |
| 专家评审 | 每个版本 | 论文要求发布前评审，未报工时 |
| 在线执行 | 每次 | 「几分钟 vs 数个工作日」（定性） |

**为什么以前不行、现在行**：

- **能力阈值**：LLM 能在约束下从元数据/文档生成候选本体，并用问题验证来筛错——2026 年前这条循环不稳定。
- **工具**：版本化本体 + 语义契约检索 + ReAct 执行，让「先语义、后执行」在工程上可落地。

## 7. 质量与边界

- **准入**：`admitted`——I1（ICDM 2026 Demo track）+ I2（联通软研院 + 南开大学）；但 demo track 权重较轻、单企业、40 问，引用时按「单公司自述」对待。
- **可核性**：Table I 与 PDF 在库；工时对比无法复算。
- **与 05 的分级**：05 记 **A**——有规模、有失败/限制、有同行评审（demo）。

## 8. 与仓库判断的关系

- **E-28（底座 + 薄本体）**：支持。联通的长在既有企业数据表与指标资产上，本体是「报表语义契约」，不是从零建塔。
- **E-29（失败在语义/权限/维护）**：**部分支持**。它的失败形态是「数对了但口径/范围错」，属于语义定义失败；但没有权限/影子实体/维护的披露。
- **E-31（成本拐点降建不降养）**：**支持且加强**。「建本体」从一周到数小时是「建」的降本；但版本迭代、专家评审、问题验证仍是长期工作——「养」没消失。
- **E-30（证据不对称）**：中国侧多一条**企业自述生产证据**（A probation），且是**甲方自己写的**（联通软研院），比厂商案例强；但仍不是外部客户采用。

## 9. 还没解决 / 下一步

- 40 问太小：需要更大评测集与错误分析。
- 没有「自动本体 vs 人工本体」对照：这是它和 05 里「人工语义层」路线之间最关键的一格。
- 没有成本账本：工时是定性对比。
- 没有失败率/维护数据：本体版本多久更新一次、谁维护，未报。
