# Glyph：给 340 万列打敏感性标签——标签层能到哪，执行层还没到

> 自包含消化：不假设你读过论文或 `card.md`。先讲清企业目录为什么自己打不了标签，再看两个 agent、三条策略与 RRF 怎么分工，逐条核 `0.55→0.92`、`F2 0.890`、`99.8%` 各自的条件与样本，最后给出对 `01/access-control` 与 04 C.1 的可用结论。**一句话：这是标签层（label）、不是执行层（enforce）的证据。**

## 0. 三句话

1. **它问什么**：企业数据目录里「这列是什么」和「这列算哪类敏感数据」长期欠账；而最敏感的那批表恰恰**不许先读数据再分类**（读了才分类 = 治理禁止的动作）。能不能只用**元数据 + 生产该列的代码**，在百万列规模上自动生成描述、并打上受治理的敏感性标签？
2. **它怎么做**：两个 LangGraph agent。**Descriptor** 用企业 GitHub 代码搜索做 active RAG（按表批量、≤50 列/次）生成列描述，再由 LLM-as-Judge 打分回炉（默认 ≤2 轮）；**Tagger** 三策略并行——description tagger（LLM 从本体语义检索出的候选里选）、LOB regex tagger（专家规则）、metadata tagger（微调 6 层 MiniLM + 精确内积向量库 + LLM 重排）——用 **RRF(k=60)** 融合，再按本体敏感性 tier 重排，每个标签留 source/score/reasoning。
3. **它发现什么**：编码器微调把**同标签检索**从 NDCG@10 **0.5497 → 0.9225**、MAP@100 **0.1888 → 0.9009**（同一 stock MiniLM 的前后对比、列级留出、同分布，**检索指标**）；端到端 curated 集上 recall-weighted **F2 = 0.890**（G1 0.878 / G2 0.961 / G3 0.938），但最强单策略 metadata-only 已有 **0.880**——融合只多 **+0.010**；生产 6 周 steward 接受率 **63.3% → 99.8%**（~24,000 判定对，作者自称 association 不是因果）。

## 1. 它解决什么问题

现代分析组织的数据目录有几十万张表、几百万列，每列上线前要回答两个问题：**它是什么意思**（documentation）与**它装的是哪类数据**（classification / governance）。现实里两者都靠人：描述缺、过期；敏感性标签落后发现几个月，PII 往往是**出事之后**才被追认。作者把这种状态叫 documentation debt，并给出量级论证：单一组织生产目录约 **3.4M 列 / 98,000 表**，即便按「专家每分钟标一列」这种高度乐观的速率，也要约 **30 人年**（§1, p.1）——算术上：3.4e6 分钟 ÷ 60 ÷ 约 1,900 小时/年 ≈ 29.8 人年（`推测`：作者未写每年工时，按 1,900 h 反算）。

难的地方不只是量。**第一，值不能用。** 对最敏感的表，读 cell value 去分类正是治理在分类完成前禁止的动作——这是个鸡生蛋约束，value-based 扫描器（Sherlock/Doduo/Presidio 一类）在这里根本跑不了。**第二，标签空间不是开放域类型。** CTA 文献（VizNet 78 类、SOTAB 91 类）的标签是「这是什么类型」，Glyph 的标签是**治理决定**：多标签、层级化、每个标签带敏感级，而且分布极度偏斜（内部非敏感类 `NON_SENSITIVE` 约占 **72%** 的列）。**第三，输出要能被审计。** 合规场景不只需要一个标签，还需要「凭什么给这个标签」。

所以论文的赌注不是「换个更强的模型」，而是**冗余 + 有原则的融合**：规则精确但脆、稠密检索能泛化但会漂、LLM 会推理但会幻觉，用 RRF 与本体校验调和，再用一个 autograder 把开放式生成变成可测任务。

## 2. 术语

| 术语 | 用大白话说 |
|---|---|
| **LOB** | line of business，企业业务线；本文用它切分评估集（G1–G3）。 |
| **Data Classification Ontology / leaf annotation** | 本文的标签空间：一份**受治理的内部**分类法，**275 个叶节点**（annotation，如 `USER_NAME` / `USER_ID` / `EMAIL_ADDR`；每个还带若干维度，其中一个是敏感级），内部节点是分类类目（如 PII 类）。**不是** Schema.org/DBpedia 那类公开词表。 |
| **NON_SENSITIVE** | 内部非敏感类，占约 72% 的列——分布偏斜的根源，也是「准确率好看」的主要来源。 |
| **sensitivity tier** | 标签的敏感级别。正文只出现「levels 2, 3, 4」与「untiered / 更高敏感」，重排时按 tier 给权重。**级数、命名、各级占比未报告。** |
| **CTA** | column type annotation，给列打语义类型标签的任务；本文把它改成「打受治理的敏感性标签」。 |
| **metadata key** | `catalog.database.table.column` 这个字符串；metadata tagger 的唯一输入（长类型截断到 200 字符）。 |
| **active RAG** | 不是固定检索一次，而是让 LLM 在 tool loop 里自己决定查什么（这里查企业 GitHub 代码），再据结果写描述。 |
| **RRF** | reciprocal rank fusion：只按名次融合多路排序，不需要把不同来源的分数校准到同一尺度。 |
| **NDCG@10 / MAP@100** | 检索排序质量指标；MAP 奖励「把同标签的邻居全捞出来」，对大小不一的标签组更公平。 |
| **F2** | β=2 的 F-measure，召回权重是精确率的两倍；本文的主选指标，理由见 §4.3。 |
| **per-tag provenance** | 每个标签都带「哪路来源、多少分、什么理由」，例如 `[sources: ann=0.92]`。 |
| **steward** | 数据管家；生产里由他们逐条接受/拒绝系统建议，判定回写成训练数据。 |

## 3. 它怎么做

### 3.1 骨架：两个可独立部署的 agent

两个 agent 各自是一张 LangGraph 有向图（节点 = 对 typed state 的纯函数，边 = 普通/条件边），节点由 builder 注入依赖（catalog client、LLM handle、检索服务），与 I/O 解耦；state 是 Pydantic 模型，每一跳都校验；配置三层（环境默认 → 部署级 `AgentConfig` → 请求级 `HyperParams`）。两者都 `temperature=0.0`、限制 token、按请求创建 LLM handle（§4.1, p.3；Fig. 1, p.4）。Descriptor 产出的描述正好是 description tagger 的理想输入，所以可以串起来，但不串也能各自跑。

### 3.2 Descriptor：四段 + 一个 judge 回路

| 阶段 | 做什么 | 关键参数 |
|---|---|---|
| `fetch_schema` | 查企业数据注册表，取列名、类型、已有描述 | — |
| `analyze_batch` | **核心**：一整张表的列放进**一次** LLM 调用（≤50 列/批）；给模型一个 `GitHub Enterprise code search` 工具，让它自己决定查什么、读匹配点周围的上下文，把描述落在**产出该列的应用代码**上；**不读 cell value** | 每列默认 **3 次**工具调用预算，批级封顶后强制收尾；代码搜索限流：60 s 窗口内 25 次后主动停 2 s，指数退避（初值 30 s、翻倍、最多 5 次）（§4.2 + 脚注 2, p.4） |
| PII 标记 / 表级摘要 | `user_id` 这类列加显式 PII 警告（autograder 直接给「PII 意识」打分）；再把列级结果合成表级业务用途摘要 | 与值级扫描器（Presidio/Cloud DLP）的分工：值是不可辨格式的哈希时格式检测抓不到，代码/元数据可以 |
| `grade_results` | judge 按四个标准打分：plausibility / specificity / completeness / PII awareness，**固定权重 0.35 / 0.25 / 0.25 / 0.15**；默认用**与生成器不同的模型家族**（避免自评偏好）；低于阈值的列带反馈回 `analyze_batch`，重试时优先重搜得分最差的列 | 默认 **≤2 轮**（§4.2, p.4–5） |

**失败模式**：代码搜不到（新服务、私有仓、命名不含业务词）时，描述退化为「按列名猜」——论文没给 RAG 失败率的测量（`推测`）；judge 的阈值与「够不够好」标准未报告；重试上限 2 轮意味着差列就那样交付。

### 3.3 Tagger：三条策略，输入/输出/失败模式各不相同

设计意图是**让三路失败模式不相关**，融合才有意义（§4.3, p.5）：

| 策略 | 输入 | 输出 | 失败模式（作者自述 + 表里能看到的） |
|---|---|---|---|
| **Description tagger** | `"{name}: {description}"`（无描述时只用列名）→ 用**未微调的** all-MiniLM-L6-v2 检索本体 annotation 的自然语言定义（cosine ≥ 阈值 `C`）→ LLM 从候选里选并排序 | tags + reasoning | **只覆盖有描述的列**（Table 3 脚注 † 明说无描述列 out of scope）；单跑 F2 **0.238**；候选阈值 `C` 未报告 |
| **Regex tagger** | 列名 | 命中即固定标签（如 `email` → `EMAIL_ADDR`）；规则由领域专家按 LOB 手写 | 只覆盖手写模式；**规则外几乎不发火**（作者原话），单跑 F2 **0.050**；规则表未公开 |
| **Metadata tagger** | 只有 metadata key（截断 200 字符）→ **微调**编码器 → 精确内积（flat）索引 → 相似度 ≥ 阈值 `S1` 的历史邻居 tags 作候选 → LLM 重排 | tags + `[sources: ann=0.92]` 形式的多源归因 | 索引是「已验证的指派」语料，**新标签冷启动**没有邻居；同分布外（新命名习惯/新 LOB）未测；单跑 F2 **0.880**；`S1` 未报告 |

值得单独记住的两点：**(a)** 只有 description tagger 过 LLM-as-Judge 自改进循环（其余两路直接进融合）；**(b)** 向量库是「已验证的人工指派」，也就是**历史标签的回声**——这既是它最强的原因，也是它最难迁移的原因（`推测`）。

### 3.4 融合：RRF(k=60) + tier 重排

三路输出的分数不可比（ANN cosine、LLM 置信度、二值规则命中），所以不做校准，直接融合名次：

```
rrf(t) = Σ_{i ∈ 含 t 的活跃列表} 1 / (k + r_i)        k = 60，r_i 从 1 起
归一化分母 = n_active / (k + 1)                       # 全部来源都排 #1 时的理论最大值
```

于是融合置信度落在 [0,1]，只有「所有来源都把它排第一」才等于 1.0。同一标签被多路提名时，按固定优先级 `llm_desc_tagger > llm_metadata_tagger > regex_tagger` **继承其中一路的 provenance**（reasoning / ontology / grades），但置信度用跨源 RRF 分；去重按 annotation 名，排序用 annotation 名做确定性 tie-break（§4.3.4, p.5–6）。

最后 `tag_normalizer` 按敏感级重排：`α·c + (1−α)·w`，`c` 是 RRF 置信度，`w` 是本体 tier 权重——untiered 与更高敏感 = **1.0**，更低敏感的第 2/3/4 级 = **0.75 / 0.5 / 0.25**；低于最低归一化分的标签直接丢弃（§4.3.4, p.6）。**`α` 未报告**，各级占比未报告。

### 3.5 一个具体例子（Table 1, p.6）

列：某国家码列，描述是「The 2-letter ISO 3166-1 alpha-2 country code.」。三路投票：regex → `INTERNAL`；description → `COUNTRY`；metadata → `COUNTRY` 且 `NON_SENSITIVE`。表中 RRF 分数：`INTERNAL 0.333`、`COUNTRY 0.667`、`NON_SENSITIVE 0.328`。

按公式复算（3 个活跃列表，分母 = 3/61 = 0.04918）：`COUNTRY` 两路第一 = (2/61)/0.04918 = **0.667**；`INTERNAL` 一路第一 = (1/61)/0.04918 = **0.333**；`NON_SENSITIVE` 一路第二 = (1/62)/0.04918 = **0.328**。三个数都对得上（`已核`，按公式算）。注意融合后的次序 `COUNTRY > INTERNAL > NON_SENSITIVE` 只看名次、不看敏感级——这正是后面 tier 重排要修的东西；但 α 与这几个标签的 tier 值未报告，**重排后的最终输出未报告**。

### 3.6 编码器：唯一被认真微调的部件（§4.4, p.6）

- **为什么**：metadata key 简短、多缩写、非自然语言；stock 模型不知道 `uat.core_db.users.uid` 与 `prod.analytics.events.user_id` 是同一概念（作者举的例子）。
- **训练数据**：从生产系统抽 `metadata_key → tags` 的**已验证**指派；同标签内任意两列构成 (anchor, positive) 对；因为 `NON_SENSITIVE` 占 ~72%，**每标签最多 3,000 对**并设最小分组门槛，最终 **70,948** 对平衡样本。
- **目标与索引**：`MultipleNegativesRankingLoss`（scale 20，cosine）——batch 内其他 positive 当负例，同标签靠近、异标签推远；索引为精确内积（flat）、向量 L2 归一，编码器与索引都版本化并发到 S3 兼容存储、容器冷启动只读加载，索引重建时**不带 tag 后缀**嵌入以免 train/serve skew；10²–10⁵ 向量够用，**过 10⁶ 要换量化/图索引**（作者明说）。

## 4. 结果：数字与条件

### 4.1 规模、本体与标签空间

| 数字 | 条件（数据/设置/样本） | 它意味着什么 |
|---|---|---|
| ~3.4M 列 / ~98,000 表 / 4 条业务线 / 3 种后端 | 单一组织（Apple）的生产目录；后端为 Iceberg、RDBMS、Cassandra（§1, p.1） | 平均约 35 列/表（`推测`，算术：3.4M/98k）；跨后端是设计动机之一 |
| ~30 人年 | 按「1 列/分钟」标完这 3.4M 列；作者称 highly optimistic（§1, p.1） | 手工不可行的量级论证，不是实测工时 |
| 275 个叶标签 | 内部 Data Classification Ontology（摘要 p.1；§3, p.3） | 标签空间是**受治理的内部资产**，不是公开标准 |
| ~72% | `NON_SENSITIVE` 占列比例（§1 p.1、§3 p.3、§4.4 p.6 三处一致） | 类别极度偏斜；F1/F2 好看的一大半来自多数类 |

本体的结构（按 §3, p.3 与 §4.3.4, p.6 能确定的部分）：**叶 = 275 个 annotation**（`USER_NAME`、`USER_ID`、`EMAIL_ADDR`…），**内部节点 = 分类类目**（如 PII 类），层级「从 generic 到 specific」；每个 annotation 除名字外还带若干维度，其中一个是**敏感级 scale**。敏感级只露了「levels 2/3/4 → 权重 0.75/0.5/0.25、untiered 与更高敏感 → 1.0」这一句，**级数、命名、各级标签数与列占比均未报告**；由权重随级号下降可推「级号越大越不敏感、至少 4 级」（`推测`）。多标签：每列输出本体子集 `Y ⊆ O`，每个标签带 confidence 与 justification（§3, p.3）。**是否为自建**：是——正文标签名是占位符，真实内部代码保密（§3 脚注 1, p.3）；是否对齐外部标准（GDPR/PCI 之类）**未报告**。

### 4.2 编码器检索（Table 2, p.6）

| 指标 | 微调前 | 微调后 | Δ |
|---|---|---|---|
| NDCG@10 | 0.5497 | 0.9225 | +0.3728 |
| MRR@10 | 0.7875 | 0.9469 | +0.1594 |
| Acc@1 / Acc@5 | 0.7138 / 0.8812 | 0.9229 / 0.9797 | +0.2091 / +0.0986 |
| MAP@100 | 0.1888 | 0.9009 | +0.7121 |

**条件（缺一条这个数就不能引）**：比较对象是**同一个 stock all-MiniLM-L6-v2 的微调前后**（不是任何 CTA 基线、不是端到端 tagging）；query 是每标签随机 10% 的**列级**留出、每标签最多 500 条 → **9,242 条 query** 对 **83,229 条 corpus**；相关集 = 该标签在 corpus 里的**全部**条目（`NON_SENSITIVE` 巨大、稀有标签只有几条），所以 recall@k 低而 accuracy@k 高；作者的限定原话是「列级留出 → 同表列可能同时在 query 与 corpus → **in-distribution 上界，未控表内泄漏**」；Table 2 caption 明说「these are retrieval, not tagging, metrics」。

**怎么读**：`0.55→0.92` 是**候选召回/排序**能力的提升，它给 metadata tagger 设了一个**上界**，不直接等于打标变准；MAP@100 的 +0.71 比 NDCG 的 +0.37 更能说明「微调后能把大小不一的同标签池捞全」。另外论文另有一套**表级不相交**的切分（(catalog, db, table) 粒度，每标签 ≥30 测试 / ≥90 训练）用于建向量检索语料——它和上面这套列级留出**不是同一个切分**，别混着引（§4.4, p.6）。

### 4.3 端到端 F1 / F2（Table 3, p.7）

**条件**：4 个由 steward 按业务线编写的评估文件（`{column metadata, expected tags}`），归成 3 组；micro-averaged；**1,905 张评估表**与 **15,205 张表的向量索引**表级不相交（§5, p.7）；LLM 为 Claude Sonnet 4.5；`F2 = 5TP/(5TP + 4FN + FP)`。**每组/每配置的样本量（列数）未报告**，无置信区间，单次运行。

| 配置 | F1 G1 | G2 | G3 | 总 | F2 G1 | G2 | G3 | 总 | p50 延迟 |
|---|---|---|---|---|---|---|---|---|---|
| Regex tagger only | 0.062 | 0.103 | 0.128 | 0.077 | 0.040 | 0.067 | 0.085 | **0.050** | 0.30 s |
| Description tagger only（Sonnet 4.5） | 0.122 | 0.326 | 0.411 | 0.205 | 0.250 | 0.325 | 0.590 | **0.238** | 47.31 s |
| Metadata tagger only | 0.890 | 0.969 | 0.956 | 0.912 | 0.853 | 0.957 | 0.937 | **0.880** | 40.41 s |
| Fusion（Sonnet 4.5） | 0.878 | 0.951 | 0.932 | 0.897 | 0.878 | 0.961 | 0.938 | **0.890** | 57.80 s |

- **F2 为什么是主指标**：作者的成本模型是不对称的——漏标一个敏感列（FN）会**静默地**击穿访问控制与合规，通常事后才被发现；误标（FP）改起来便宜，steward 复核时顺手就否了。所以 β=2，召回权重是精确率的两倍（§5, p.7）。
- **F2 比 F1 低**这件事值得注意：metadata-only 与 fusion 的 F2 都低于自己的 F1（0.880<0.912、0.890<0.897）。F_β 随 β 单调上升当且仅当 R>P，所以这两行说明**召回低于精确率**（`已核`，算术）。作者通篇没给 P/R（尽管正文说「we report precision, recall, F0.5, and F1 for completeness」），**P/R/F0.5 在表里都不存在 → 未报告**。
- 三组之间的差很大（regex G3 0.085 vs G1 0.040；description G3 0.590 vs G1 0.250），说明**组间难度/标签构成不同**；但组怎么分、每组多少列、对应哪条业务线，**未报告**（正文只说 4 个评估文件、3 组，而目录有 4 条业务线——对应关系没写）。
- 一处**正文与表不一致**：作者写「under F1 the fusion and the metadata tagger are tied」，表里是 0.897 vs 0.912（差 1.5 pp，不算 tied）；同一句还说「under F0.5 the single strategy leads」，**F0.5 未在表中出现**。引用这句要回表核（`已核` 数字；表述 `存疑`）。
- description tagger 只评「有描述的列」，而 caption 说「all runs cover the same 4 evaluation files」——**有描述的列占多少、无描述列怎么计入 micro 平均，未报告**，这个口径直接影响 0.238 与 0.890 的可比性。

### 4.4 消融怎么读：贡献不在你以为的地方

论文自称做了「isolating each strategy and the RRF fusion」的消融，实际只有**四配置**：三路各自单跑 + 全融合。**没有 leave-one-out**（fusion 减 regex、fusion 减 description）、没有两两组合、没有 `k` 的消融、没有 tier 权重 `α` 的消融、没有 judge 开/关的消融。

由此能得到的最硬读数是（`已核` 数字，`推测` 归因）：

| 读数 | 数 | 含义 |
|---|---|---|
| 融合 vs 最强单策略 | F2 0.880 → 0.890（**+0.010**）；F1 0.912 → 0.897（**−0.015**） | RRF 的端到端增益很小，且在无 CI 的单次运行上不足以证明「融合有效」；换 β 就翻转——作者也承认排序是 β 依赖的 |
| 编码器微调（MAP@100） | 0.1888 → 0.9009（**+0.7121**） | 增益量级是融合的约 70 倍（+0.71 vs +0.01；两者不是同一指标，只比量级）→ 这套系统的质量主要来自**微调编码器 + 已验证的历史指派**，不是多 agent 编排（`推测`） |
| 三路中两路单跑几乎不可用 | regex 0.050、description 0.238 | 它们「earn their place only as an input to the fusion」（作者原话）——但表里看不出它们各自贡献了多少 |

**结论**：这是一次「每路单独 vs 全部」的对照，不是真正的贡献分解。想回答「RRF 值不值」，需要 leave-one-out 与重复运行；论文没做（`已核`，按表与正文）。

### 4.5 生产接受率（Fig. 2, p.7；§5.2）

| 数字 | 条件 | 怎么读 |
|---|---|---|
| 63.3% → 99.8% | 连续 6 周、**~24,000** 条 steward 判定、周频回写并重训编码器 | 接受率的**趋势**；图纵轴自 **50%** 起，视觉斜率被放大 |
| 21× | 同一窗口内判定量的增长 | 受审人群同时在扩大 |
| 「association 不是因果」「precision-like，对 FN 盲」 | 作者原话 | 判定量涨 21×、人群变宽 → 不能归因给系统变好；steward 只看得到系统**吐出**的标签，没被提议的敏感列根本不进判定 → 接受率**结构上无法反映漏标** |

`推测`（我的推断，非作者结论）：接受率上升至少有三个未分离的来源——(a) 系统每周重训确实变好；(b) steward 习惯/自动化偏见；(c) 受审样本的难度构成变化。要拆开需要「固定一批列、不随系统更新复判」的对照，论文没有。

### 4.6 延迟与成本

p50 请求延迟（Table 3, p.7）：regex **0.30 s**、description **47.31 s**、metadata **40.41 s**、fusion **57.80 s**。description tagger 花掉 fusion 延迟的 **82%**（47.31/57.80 = 81.9%，作者写 82%），却只换来 0.238 的 F2——这是「它不能单独部署、只能当融合输入」的成本论据。全文**没有美元成本、没有吞吐、没有 batch 并行后的数字**；「把整表列放进一次调用是主导延迟/成本的那个比值」是定性判断（§6, p.8）。Descriptor 侧的成本以**预算**形式出现：每列 3 次工具调用、批级封顶、限流与退避参数——是工程约束，不是测量结果。

## 5. 这些数字不能说明什么

1. **不能外推到别的企业。** 全部数字来自**单一组织的单一生产目录**（4 条业务线、3 种后端），标签空间是内部 275-leaf 本体。换组织=换本体、换命名习惯、换历史指派语料，三条策略的相对强弱都会变（`推测`）。
2. **0.55→0.92 不是 tagging 精度，也不是对公开基线的提升。** 它是同一编码器微调前后的**检索**指标（Table 2 caption），且作者自认是**未控表内泄漏的同分布上界**。把它写成「Glyph 打标准确率 92%」是错的。
3. **0.890 的 F2 不是 gold 上的 F2。** 期望标签是 steward 写的 curated expectations，覆盖是否完整、无标签列怎么算均未报告；组间差异（0.250–0.590）大于配置间差异，说明**组构成**的影响可能比方法更大。而且**没有 P/R、没有每组样本量、没有 CI、没有重复运行**——论文声称报 P/R/F0.5，表里没有；小数点后三位（0.897 / 0.890 / 0.880）不要当精确值读。
4. **没有 OOD。** SOTAB/GitTables 只被点名为「usable out-of-distribution probe」和「concrete near-term work」（§2, p.2–3），**没做**。跨企业、跨目录、跨行业一律未测。
5. **judge 与阈值都没校准。** LLM-as-Judge 的四个权重（0.35/0.25/0.25/0.15）是拍定的，**judge–human agreement 被作者自己列为「尚未证明」**（§7, p.8）；余弦阈值 `C`、相似度阈值 `S1`、混合系数 `α` 的取值全部未报告。
6. **"graceful degradation" 只有摘要里那一次。** 正文没有定义、没有故障注入、没有降级后的指标 → **未报告**。可勉强对应的机制是：RRF 按**活跃列表数**归一（少一路也能算）、provenance 优先级回退、低于阈值丢弃、judge ≤2 轮（`推测`）。
7. **接受率不能当"部署有效"。** 它是 precision-like、对 FN 盲、且作者自称 association；**漏标率、未标注率、覆盖率的绝对值全文未报告**。这正是访问控制最需要的那个数。
8. **Table 4 的跨系统对比只是定位。** taxonomy（275 内部标签+敏感级 vs 78–91 开放域类型）、标签基数、输入信息（元数据+代码 vs cell value）三者都不同，作者自己写「not directly comparable」，prior-work 数字是各自最佳配置的转载——**不能当 head-to-head**。
9. **没有 enforcement。** 全文没有策略引擎、ACL/ABAC、拒绝率、执行点；"needed for access control" 是动机句，"per-request authentication" 是服务调用认证。**标签质量 ≠ 策略正确 ≠ 执行正确**（见 §8）。

## 6. 工程上怎么用

**复刻顺序（别从多 agent 编排开始）**

1. **先定标签空间**：叶节点 + 层级 + 敏感级。这是最大的一次性资产，也是本文**最不可复刻**的部分（内部本体不公开）。没有受治理的本体，后面全是空转。
2. **先做 metadata-only**：拿「已验证的历史指派」造 (anchor, positive) 对，按标签封顶（本文 3,000/标签）防多数类淹没；in-batch contrastive 微调一个小编码器（本文：6 层、384 维、~90 MB）；建 flat 内积索引（10⁵ 级别够用，过 10⁶ 再换索引）。在**表级不相交**的留出上看检索（NDCG/MAP）与端到端 F2。
3. **把评估口径写死再谈优化**：micro-F2、β=2 的理由（漏标贵）、期望标签谁写、无描述列怎么算、未标注列怎么算。本文这几处没写清，是可复现性的主要缺口。
4. **再加另外两路**：description tagger 需要有人工描述或代码 RAG（没有描述时它不覆盖）；regex 只在该 LOB 的命名规范稳定时才有意义。**加之前先量它们在表级留出上的边际贡献**（本文只有「单独 vs 全部」，你得自己补 leave-one-out）。
5. **生产回路**：steward 判定 → 回写 → 周频重训编码器。**同时**独立抽样估漏标（接受率结构上看不见 FN）；没有这个数，不要把它接进授权链路。

**关键参数**

| 项 | 本文取值 | 备注 |
|---|---|---|
| RRF `k` / tier 权重 | 60 / 1.0·0.75·0.5·0.25（按敏感级） | 都没做消融；`α` 未报告 |
| Descriptor 批量 / 代码搜索预算 | ≤50 列/次；3 次/列，批级封顶后强制收尾 | 批量是成本主导项；限流 25 次/60 s 后停 2 s，退避 30 s 起、翻倍、≤5 次 |
| judge | 4 标准固定权重，异家族模型，≤2 轮 | 阈值未报告 |
| 编码器输入 | metadata key，截断 200 字符（按分隔符切） | 与训练格式对齐 |
| 索引 | flat 内积、L2 归一、10²–10⁵ | >10⁶ 需量化/图索引 |
| 训练对 | 70,948；每标签 ≤3,000 | `NON_SENSITIVE` 占 72%，必须封顶 |

**何时用 / 何时别用**

- **用**：有受治理的本体与稳定命名规范；有历史人工指派可当训练/检索语料；表**不允许读值**或读值成本极高；能接受「标签是建议、有人复核」的工作流。
- **别用**：没有本体（标签空间会漂）；没有历史指派（metadata tagger 冷启动）；命名靠随机 ID/哈希且无代码可查（三路都失效）；需要**保证**（这套没有任何健全性保证，也是概率输出）；要直接当**授权判定**（它不做策略，见 §8）。

## 7. 质量与边界

- **证据类型与强项**：生产系统报告（preprint，无同行评审），含真实部署的人审回路、四配置消融、三组 curated 评估、一个可复算的融合示例；口径写得诚实——自己指出列级留出的表内泄漏、接受率对 FN 盲、β 依赖、与公开 CTA 不可比；把失败面写出来（regex 单跑 0.050、description 单跑 0.238 且延迟 47 s）；工程参数具体到批量、预算、限流、索引规模；`已核` 门槛低（数字与公式都能复算）。
- **主要威胁**：① 单企业单目录，本体与代码不公开 → **不可复现**；② 无 OOD、无公开基准；③ 无 P/R、无每组样本量、无 CI、单次运行；④ judge 未校准且作者承认 judge–human agreement 未证；⑤ 评估集由 steward 编写，但选列/选标签规则未报告（选择偏差未知）；⑥ 依赖单一商业 LLM（Claude Sonnet 4.5）→ 时间敏感；⑦ `graceful degradation` 与 abstract 若干说法在正文没有对应证据。
- **`quality: B` 的理由**：按仓库定义，A 需「多基准 / 真实部署 / 消融」——本文有后两项，但**没有第一项**（无公开基准、无 OOD），且唯一部署证据是「对 FN 盲的接受率」，同时缺 P/R 与方差。故判 B：机制与数字可核、单域有限评估，不到 A。
- **引用时必须带上的限定**：Apple 单企业单目录（3.4M 列 / 98k 表 / 4 LOB / 3 后端）、内部 275-leaf 本体（不公开）、列级留出同分布检索、Claude Sonnet 4.5 + 自微调 MiniLM、F2 口径；**是标签层证据，不是授权/执行证据**。

## 8. 与仓库判断的关系

### 8.1 `execution_form: label` 的判定（`已核` 依据 + `推测` 定级）

本体在 Glyph 里干三件事：**(a)** 当**封闭标签空间**（候选约束 + 事后 membership 校验，幻觉标签被拒）；**(b)** 当**候选来源**（annotation 的自然语言定义被嵌入、检索、塞进 prompt）；**(c)** 当**重排权重**（敏感级 → `w`）。它**没有**被求值：没有 entailment、没有 SHACL/OWL 约束检查、没有查询重写、没有一致性校验。所以 `label` 是主档；`context` 只描述了 (b) 这一半（本体文本确实进了 prompt，但作用是「候选标签」而非「世界知识」）。若仓库以后要单列「本体当候选约束」一档，Glyph 可作样本之一——**但在现有五档里 `label` 最贴近**。

### 8.2 与 E-20、trustgraph、commit-gate F5–F7 的关系

- **E-20（本体执行的形态分类）**：Glyph **不属于 `engine`**。E-20 的四种 `engine` 都涉及本体被求值（OWL 2 QL 重写、SHACL-AF 策略求值、SHACL 校验、SHACL→SPARQL 编译）；Glyph 只把本体当标签空间与候选集。它是本仓库里 `label` 形态**最清晰的一个样本**（GGC 判 `none`，只在「schema 进权重」这点上贴近 label），可与 trustgraph 的 SHACL-AF **求值**形成对照：**同一份敏感性本体，一边当标签、一边当策略求值，是两层、不是两种实现**（`已核`：按定义；跨层对比 `推测`）。
- **trustgraph（`01/access-control` F2 的锚点）**：做的是**读路径结果过滤**——`sh:SPARQLTarget`/`sh:SPARQLRule` 求值、异常 fail-open、只删 subject 侧（commit-gate F5–F7）。两者**不可互证**：Glyph 证明「标签可大规模产出且有审计线索」，trustgraph 证明「策略可在读路径执行（但不健全）」；把两者接起来还缺一段**没人写**的接口——标签 → 策略主体/资源属性 → 判定（`推测`，本仓库缺口）。
- **commit-gate F5–F7**：Glyph 无执行路径，故与 fail-open/subject-only **无从直接对照**。但有一处**同构风险**值得记：Glyph 对低于阈值的标签直接**丢弃**，对「三路都没覆盖」的列**没有兜底**，而**未标注率/覆盖率全文未报告**——从授权角度看，这等价于把「没打上标签」的列留给下游默认处理，与 F6 的 fail-open 是同一类设计选择（`推测`，**不是**作者结论；作者从未讨论未标注列的下游处理）。
- **与 `01` 派其它判断**：不触及 01-L1…L15 中的任何一条（那些是动作前可逆性/验证条件/审批成本）；Glyph 补的是**授权输入侧**的证据。

### 8.3 对 04 C.1 的可用结论

C.1 要分的是**三层**，Glyph 只填第一层：

| 层 | 谁回答 | 本文能给什么 | 不能给什么 |
|---|---|---|---|
| **标签 / 分类** | 这列是什么、算哪类敏感 | 生产级机制：value-free、code-grounded、三策略 + RRF、per-tag provenance；量级 3.4M 列 | 漏标率、跨企业迁移、标签到策略的映射 |
| **策略** | 谁在什么条件下 allow/deny | **什么都没有** | 策略语言、冲突消解、默认拒绝 |
| **执行** | 在哪拦、拦不住怎么办 | **什么都没有**（trustgraph 才在这层） | fail-open/fail-closed、方向性、写路径 |

可直接写进 C.1 的句子：**「标签层产出的是策略的输入，不是判定：Glyph 在 Apple 单目录上把列级敏感性标签做成可运行的服务（不读 cell value、per-tag provenance），但没有策略引擎、没有执行点、没有漏标率；它的指标是标签质量，不是授权正确性。」**（数字留在 F1 里并带上条件，C.1 只写分层） 等级：`已核`（机制与数字，一手正文）/ `推测`（跨企业、以及「未标注≈fail-open」的类比）。

**哪些数字不能进 04**：`0.9225` / `0.9009`（检索、同分布、可能表内泄漏）、`0.890`（单企业 curated 集、无 P/R 无 CI）、`99.8%`（precision-like、对 FN 盲）、`275`（内部本体，不外用）。**能进 04 的是机制与分层，不是这些数**。

### 8.4 建议 F1 / F2 措辞（供 `01/access-control` 落盘）

> **F1（标签层）**：Glyph（Apple 生产目录：~3.4M 列 / ~98k 表 / 4 条业务线 / 3 种后端）证明**标签层可以工程化**：内部 **275-leaf** 敏感性本体、**不读 cell value**（只用元数据键 + 生产代码）、三策略并行 + **RRF(k=60)** + 敏感性 tier 重排、每标签带 source/score/reasoning。质量读数：编码器微调使同标签**检索** NDCG@10 0.55→0.92、MAP@100 0.19→0.90（同一 stock MiniLM、9,242 query / 83,229 corpus、列级 10% 留出、**同分布上界**）；端到端 curated 集 **F2 0.890**（G1 0.878 / G2 0.961 / G3 0.938），仅比 metadata-only 0.880 高 0.010。**等级：`已核`（机制与数字，一手正文；生产部署为作者报告）/ `推测`（跨企业、跨目录）。**
>
> **F2（执行层，措辞不变但需加界）**：执行层另有其物——trustgraph 用 SHACL-AF 对**读路径**结果做策略过滤，异常 fail-open、只删 subject 侧（[E-20]、commit-gate F5–F7）；写路径 commit gate 仍无实现。**Glyph 的 F2/NDCG 与它不可互证**：前者是标签质量，后者是（不健全的）执行。等级：`已核`（代码）/ `推测`（综合）。

## 9. 还没解决 / 下一步

- **漏标率 / 未标注率（最关键）**：三路都没覆盖、或标签低于阈值被丢弃的列占多少？下游怎么处理？这是能否接进授权链路的**前置条件**，本文完全没报。
- **OOD**：作者自己点名 SOTAB/GitTables 作探针没做；跨企业第一步应是「把 275 leaves 映射到目标企业词表」，映射本身的准确率是独立问题。
- **judge 与消融**：四个权重的校准、judge 与人工判定的一致率（作者列为未证）；真 leave-one-out（去掉 regex / 去掉 description）、`k` 与 `α` 的敏感性、重复运行与 CI——现在只有「单独 vs 全部」。
- **评估口径**：每组列数、有描述列占比、期望标签的完备性。这三项不解决，`0.890` 不可跨报告比较。
- **成本曲线**：每列 3 次代码搜索是否够？加到 6 次质量涨多少？全文只有预算，没有曲线。
- **接口层**：标签如何变成策略属性（subject/resource attribute）、由谁签发、版本怎么管——本文不涉及，是本仓库 `01/access-control` 与 04 C.1 真正缺的那一段。
