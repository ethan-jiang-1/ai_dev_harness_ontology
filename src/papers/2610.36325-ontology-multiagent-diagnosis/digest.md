# MedMAS-DDx · 消化

> 事实、数字、页码回 [card.md](./card.md)。这里只写**我们怎么用**、值不值得、哪里会坏。

## 工程思路

**要做「可审计的鉴别诊断」，按这个顺序：**

1. **把 LLM 限制在语言层。** 抽取症状、生成问题、写解释；**排序/评分/更新全部用确定性代码**。这是可审计性的来源。
2. **先做症状映射，再做诊断。** canonical → alternatives → synonym/HPO fallback；映射失败的保留 trace，但不进推理。映射率（91.3%）就是系统上限。
3. **候选集只从本体关系来。** 疾病必须显式链接到至少一个患者症状；不让 LLM 生成「可能的病」。
4. **评分要能解释。** specificity（稀有症状权重）+ coverage + 追问后的 support/conflict；每一项都能回指症状与本体关系。
5. **追问只问有区分度、可观察、未报告的症状。** Yes/No/unsure 约束格式；最多 10–11 问（benchmark 显示更长的对话收益下降）。
6. **阈值宁宽勿严。** 早期丢掉的候选后面回不来；保留领头分数的一小部分或至少匹配 2 个症状。
7. **聚合指标会掩盖 case-level 价值。** Top-1 +2.5 pp 看起来小，但 Case #96 从 0.340→1.0；要同时报「可解决歧义」的子集。
8. **同时报 Top-1 与 Top-3。** 追问可能把弱候选换掉，Top-3 反而下降（50% 时 26.3→24.2）。
9. **换更强 LLM 不解决结构错。** 错误主要是本体覆盖/粒度/术语不匹配；先修本体，再换模型。

## 实用意义

它解决的操作问题：

- **「病人描述不全，LLM 直接下诊断。」** → 先抽症状、生成候选、追问缺失的区分性症状。
- **「诊断不可解释。」** → 每个分数回指症状 + 本体关系；输出 reasoning trace。
- **「LLM 编一个听起来合理的病。」** → 候选必须在本体 KG 里有症状链接；没有就拒绝输出。
- **「问太多问题，病人烦。」** → 只问有区分度的；预算 ~10 问。
- **「Top-3 里有一个对的，但 Top-1 错。」** → 鉴别诊断应按 Top-3 评估；但要注意追问可能伤 Top-3。
- **「本体里没有这个诊断。」** → 系统会拒答/追问，不会硬编；这是安全特性，也是覆盖上限。

**何时用**：有 curated 医学本体；症状-疾病关系可查；需要可审计的鉴别诊断；能接受 Yes/No 追问。

**何时别用**：开放域/罕见病；本体覆盖不足；需要 severity/temporal 细节；真人对话成本高；需要最终确诊（系统只做 differential）。

## 质量评估

- **证据类型**：实证·基准（`已核`，一手正文；小样本、模拟患者）。
- **样本与对照**：99 cases / 29 diagnoses；80%/50% 两个 completeness；N=198；MedQDx baseline；case study。
- **优点**：确定性评分 + 本体 grounding；可解释；追问机制；case-level 分析；诚实写「封顶」与「聚合掩盖」。
- **主要威胁**：小样本；模拟患者乐观；SapBERT 0.6 阈值；本体覆盖/术语不匹配；问题预算高；无真人；无跨本体。
- **`quality: B` 理由**：机制清晰、可审计；但样本小、模拟患者、单本体，外部效度有限。

## 洞察

1. **LLM 只做语言，排序交给代码，是可审计性的关键。** 不是「让 LLM 解释」，而是「LLM 的解释必须回指确定性分数」。`已核`
2. **聚合 refinement 很小，case-level 很大。** Top-1 +2.5 pp，但 Case #96 通过一个 jaundice 确认把 0.340 拉到 1.0；只报聚合会低估机制价值。`已核`
3. **追问不是均匀变好。** 50% completeness 下 Top-3 从 26.3→24.2；追问替换弱候选，可能伤 Top-3。指标要选对。`已核`
4. **curated KG 会封顶。** Jaundice/Vertigo 在 benchmark 是诊断、在本体是症状；系统按本体无法输出，准确率恒 0。**这是覆盖问题，不是推理问题。** `已核`
5. **换更强 LLM 不会修结构错。** 错误主要来自 KG 稀疏/粒度/术语；作者的判断与本仓库 E-06 一致。`已核`
6. **问题预算是一个显式成本。** ~10 问 vs MedQDx 2.4；是否值得取决于场景。`已核`
7. **Yes/No/unsure 是双刃剑。** 它让评分确定、可复现，但丢掉 severity/temporal；真实临床可能需要更丰富的回答格式。`推测`
8. **「拒绝输出」是安全特性，也是覆盖率上限。** 候选必须对应本体疾病；没有对应就不猜。`已核`

## 成本与使能条件

| 成本 | 一次性 / 每次 | 说明 |
|---|---|---|
| 本体 + KG | 一次性/持续 | SYMP/DOID/HPO；GraphDB；术语对齐 |
| 症状映射 | 每次 | 91.3% 成功；8.7% 丢失；HPO fallback |
| LLM 抽取/提问/解释 | 每次 | 3 个 agent；有调用成本 |
| 追问 | 每次 | ~10 问；患者/用户时间 |
| 评估 | 每 case | SapBERT/人工；模拟患者 |
| 维护 | 本体更新 | 新疾病/症状/术语；覆盖扩展 |

**使能条件**：curated 本体；可查的症状-疾病关系；能接受 Yes/No 追问；有审计需求。

**2022 年做会卡在哪**：LLM 症状抽取不稳；没有 Q4DX/MedDialogRubrics 这类交互基准；GraphDB/SPARQL 工具成熟但 LLM 集成不成熟。

**反向条件**：开放域/罕见病；本体覆盖不足；需要 severity/temporal；真人对话成本高；需要确诊而非 differential。

## 不可迁移

- Q4DX 99 cases / 29 diagnoses；小样本。
- 模拟患者（可访问完整 profile）是乐观估计；真人对话未测。
- 单本体（SYMP/DOID/HPO）；跨本体/开放域未测。
- SapBERT 0.6 阈值与 Top-1/Top-3 口径；换评估会变。
- Yes/No/unsure 格式限制；真实临床需要更丰富输入。
